## 1. 배치 데이터 한 덩어리

### 문제
배치는 앞으로 배치 패널에서 함(설계 0.5절). 그런데 지금까지의 시안은 방 바닥, 벽, 가구, 부착물을 씬에 손으로 놓은 것이라 패널이 고칠 대상이 없었음. "데이터를 넣으면 배가 나온다"는 경로가 필요했음.

### 후보
1. 기존 씬 오브젝트를 읽어서 데이터로 되돌리는 방식(지금 변 편집기가 하는 방식).
2. 데이터 에셋 하나를 정본으로 두고, 씬에는 빈 그룹만 두는 방식.

### 선택과 이유
2번. 씬을 읽는 방식은 "씬이 정본"이라 패널이 생기면 다시 뒤집어야 함. 데이터 에셋은 패널이 그대로 편집할 수 있고, 같은 데이터면 같은 배가 나오는지 확인하기도 쉬움.

### 구현 방식
1. 배치 데이터 에셋(`ShipLayout_Large`) 하나에 배 시드, 방 목록(왼쪽 아래 칸, 크기, 창 여부, 바닥 색), 문이 놓인 변 목록, 가구 자리, 방 조명, 그리고 구조 칸 목록이 들어 있음.
2. 시작 데이터는 확대판 시안의 방 10개, 문 11개, 가구, 조명을 그대로 옮긴 것.
3. Play를 누르면 생성기가 다른 어떤 스크립트보다 먼저 돌아서 바닥, 방 경계 벽과 문, 가구, 방 조명, 외피, 형판 부품, 구조층, 소품을 전부 만듦. 씬 파일에는 빈 그룹만 저장됨.
4. 기존 컨트롤러와 변 편집기는 고치지 않고 그대로 씀. 생성기가 만든 바닥과 벽이 예전 씬과 같은 이름, 같은 위치 규칙을 따르기 때문에 둘 다 예전처럼 동작함.
5. 방이 겹치거나 문이 맞닿은 두 거주 칸 사이가 아니면 데이터가 깨진 것이므로 예외로 시끄럽게 멈춤.

### 여기서 터진 것
- 창 여부를 그대로 옮기면 창 있는 방이 다섯 개라 구조층이 창 앞마다 잘려 빗살 모양이 됨. 계획서가 창이 필요한 방으로 꼽은 함교와 창가 방만 창을 남기고 연구실, 부엌, 숙소는 창을 끔. **데이터상 결정이라 사용자 확인이 필요함.**
- 편집 모드에서는 씬이 비어 보임. 생성 결과를 씬에 저장하면 씬 파일이 수만 줄씩 바뀌고, 저장된 결과와 데이터가 어긋날 수 있어서 일부러 Play 때만 만듦.

### 조절 가능한 것
- 배 시드: 소품 고르기와 경고등 자리가 바뀜. 배 모양(구조 칸)은 바뀌지 않음.
- 방의 창 여부: 켜면 그 방 바깥 면 앞의 구조층이 비워지고 외피에 창 벽이 붙음.

## 2. 구조층 자동 채움

### 문제
외피가 방 바로 바깥을 얇게 감싸서 윤곽이 방 배치를 그대로 따라감("호텔이 떠다니는 것 같다"). 거주 칸과 외피 사이를 채우는 비거주 볼륨이 필요하고, 그 볼륨의 모양이 배의 윤곽을 정해야 함.

### 후보
계획서 3.2절의 세 가지(한 집합에 종류 값, 별도 목록, 매번 계산). 결정 1에 따라 별도 목록을 통째로 저장.

### 선택과 이유
- 구조 칸은 거주 칸과 다른 목록이라 변 편집기와 방 계산은 손대지 않아도 됨(실제로 변 편집기가 예전과 같은 벽, 문, 방 수를 읽음).
- 자동 채움은 "목록을 새로 써 주는 도구"이고 생성기는 저장된 목록만 읽음. 그래서 채움 규칙을 고쳐도 이미 저장된 배 모양은 안 바뀜.

### 구현 방식 (순서대로)
1. **기본 띠**: 거주 칸에서 정해진 거리 안의 빈 칸을 전부 구조 칸으로 만듦. 거리를 가로세로 합으로 재서 모서리가 비스듬히 깎임.
2. **움푹한 곳 메우기**: 넓혔다가 다시 좁히는 연산으로 좁은 홈과 구멍을 메움.
3. **창 면 예외**: 창 있는 방의 바깥 면 앞으로 일정 깊이까지 구조 칸을 지움. 대칭이 켜져 있으면 반대쪽도 같이 지움(안 그러면 대칭 단계가 다시 채움).
4. **윤곽 형판**: 형판마다 기준점(뒤, 앞, 옆)을 지금 선체 모양에서 계산하고, 그 가장자리에서 바깥으로 찍음. 형판은 창 면 예외 뒤에 찍으므로 창 앞도 덮을 수 있음(형판 설계자의 책임).
5. **대칭**: 배 길이 방향 중심선 기준으로 거울 복사. 양쪽에 다른 역할이 있으면 우선순위 높은 역할(엔진 > 탱크 > 장갑 > 채움)로 맞춤.
6. **거주 칸 우선**: 어느 단계에서도 거주 칸 자리에는 구조 칸을 만들지 않음.
7. **이어받기**: 다시 채울 때 이전에도 있던 칸은 내구도를 유지하고, 새 칸은 가득 참. 사라진 칸의 손상은 버림(결정 2).
8. 결과는 좌표 정렬 순서로 저장. 해시 집합 순회 순서에 기대는 단계가 없음.

지금 들어 있는 형판: 바깥 엔진 포드(뒤, 좌우), 가운데 엔진 포드(뒤), 옆구리 탱크(옆, 반타원), 뒤로 젖힌 방열 지느러미(옆, 끝이 좁아짐), 뱃머리 집게(앞, 끝이 좁아짐). 전부 과하게 잡음(결정 8).

### 여기서 터진 것
- 창 면 예외를 한쪽만 적용하면 대칭 단계가 반대편 칸을 복사해 창 앞을 다시 막음. 예외 칸 자체를 대칭으로 만들어서 해결함.
- 형판 기준점을 "거주 칸 경계"로 잡으면 띠 안쪽에 묻힘. "지금 선체(거주 + 띠)의 가장자리"로 잡아야 실제로 튀어나옴.
- 1m 격자라 비스듬한 형판(젖힌 지느러미, 집게 끝)이 계단 모양으로 보임. 블록아웃에서는 그대로 둠. 매끈하게 하려면 비스듬한 외피 조각이 필요함(못 한 것).

### 조절 가능한 것 (구조층 프로필 에셋)
- 띠 두께: 방 바깥 기계 구역의 기본 폭. 줄이면 다시 "두꺼워진 호텔"에 가까워짐.
- 거리 재는 방식: 깎인 모서리 / 네모 모서리.
- 메우기 반경: 이 값의 두 배 폭까지의 홈이 메워짐. 윤곽을 방 모양에서 떼어 내는 핵심 노브.
- 창 앞 비우는 깊이: 띠 두께와 메우기 반경을 합친 것보다 커야 창 앞이 완전히 열림.
- 대칭 켬/끔.
- 형판마다: 켬/끔, 기준점, 역할, 모양(그대로/좁아짐/반타원), 위치, 길이, 폭, 끝 폭, 뒤로 젖힘, 몸통과 겹치는 깊이.

## 3. 외피

### 문제
외피가 이제 거주 칸이 아니라 거주 칸 + 구조 칸 전체를 감싸야 함. 구조층 윤곽에는 오목하게 꺾이는 곳이 반드시 생기고, 창은 방이 아니라 칸의 면 단위로 정해져야 함.

### 후보
1. 기존 생성기에 구조 칸을 덧붙여 읽기.
2. 선체 칸 집합과 창 면 목록을 입력으로 받는 새 생성기.

### 선택과 이유
2번(계획서 4.3절). 기존 생성기와 기존 씬은 비교 기준으로 그대로 둠. 외피 조각 프리팹은 기존 것을 그대로 재사용함.

### 구현 방식
1. 선체 칸 전부에 지붕과 밑판.
2. 이웃이 빈 변마다 바깥 벽. 그 면이 창 면이면 창 벽.
3. 두 이웃이 모두 빈 꼭짓점마다 볼록 모서리.
4. 오목 꼭짓점은 조각을 따로 두지 않음. 바깥 벽 조각이 변에서 바깥으로 튀어나온 모양이라, 오목 꼭짓점에서 만나는 두 벽이 서로 파고들어 안쪽 모서리를 스스로 닫음. 외부 화면에서 구멍이 안 보이는 것을 확인함.
5. 방 지붕 덮개(방마다 하나)는 쓰지 않음. 방 모양이 지붕에 다시 드러나면 호텔 인상이 돌아오기 때문.

### 여기서 터진 것
- 오목 모서리 조각이 필요할 줄 알았는데(계획서 4.5절), 지금 벽 단면에서는 필요 없었음. 벽 단면을 바꾸면(예: 바깥으로 튀어나오지 않는 벽) 다시 필요해질 수 있음.

### 조절 가능한 것
- 외피 조각 프리팹을 바꾸면 모든 칸에 반영됨(기존 규칙 그대로).

## 4. 형판 부품 (엔진, 뱃머리, 용골, 덮개, 등줄기)

### 문제
뱃머리, 용골, 함교 차양, 엔진이 절대 좌표로 적혀 있어서 윤곽이 커지면 엉뚱한 곳에 묻힘.

### 선택과 이유
전부 저장된 칸 데이터에서 자리를 계산함. 엔진은 구조층의 엔진 자리 위에 놓는 부품(결정 4).

### 구현 방식
1. **엔진**: 엔진 역할 칸 중 바로 뒤가 우주인 칸들이 세로로 이어진 줄을 찾고, 그 줄에 엔진을 나란히 채움.
2. **뱃머리**: 중심선 두 줄에서 선체 맨 앞 칸 바로 앞에 놓음. 맨 앞 칸이 창 있는 방이면 함교 차양도 붙임.
3. **용골**: 중심선의 선체 맨 뒤에서 맨 앞까지 늘려서 배 밑에 붙임.
4. **엔진 포드 덮개, 탱크 돔**: 같은 역할로 이어진 칸 덩어리마다 하나. 엔진 포드는 각진 덮개, 탱크는 반쯤 묻힌 돔.
5. **등줄기**: 중심선을 따라 뒤끝에서 함교 조금 앞까지 이어지는 낮은 덮개. 평평한 지붕에 높낮이를 줌.
6. 손으로 놓았던 부착물(안테나, 방열판, 탱크, 돔)은 새 씬에 없음. 방열판은 지느러미 형판으로, 탱크는 탱크 형판으로 대체됨.

### 조절 가능한 것
- 엔진 포드 덮개 높이, 탱크 돔 높이, 등줄기 높이와 폭, 등줄기가 뱃머리 앞에서 멈추는 거리. 등줄기 높이를 없애면 등줄기를 안 만듦.

## 5. 내부 뷰 단면

### 문제
뚜껑을 열면 방 바깥 구조층이 "기계로 꽉 찬 어두운 단면"으로 보여야 함. 그런데 망원 카메라가 비스듬히 내려다봐서 높이가 있는 것은 그 뒤쪽 바닥을 가림. 구조층을 높이 세우면 카메라 쪽 가장자리 방이 덮임.

### 후보
계획서 5.2절. 셰이더 자르기는 나중이고 지금은 블록아웃 상자 높이 바꾸기(결정 7).

### 선택과 이유
카메라 쪽 칸은 낮게, 반대쪽 칸은 높게 자름. 방 사이 벽 낮추기와 같은 논리(카메라 반대쪽 바깥 벽만 온전한 높이)라서 "낮은 벽 뒤에 낮은 기계, 높은 벽 뒤에 높은 기계"로 일관됨.

### 구현 방식
1. 구조층은 외피 그룹과 다른 그룹에 둠. 그래야 뚜껑 열기가 외피를 "그림자만"으로 바꿀 때 같이 사라지지 않음.
2. 구조 칸마다 단면 상자 하나. 역할마다 조금씩 다른 어두운 색.
3. 칸마다 가장 가까운 거주 칸 쪽 방향을 미리 구해 둠. 화면 방향과 그 방향이 같은 쪽이면(거주 칸이 이 칸보다 시선 앞쪽) 카메라 쪽 칸.
4. 카메라 쪽 칸은 낮은 단면 높이와 납작한 소품만, 반대쪽 칸은 높은 단면 높이와 큰 소품을 보임.
5. 컨트롤러가 뚜껑 열고 닫기, Q/E 회전 때 알림을 보내면 3~4를 다시 계산함. 컨트롤러에는 이 알림과 현재 화면 방향 읽기만 추가함.
6. 뚜껑을 닫으면 구조층 전체를 끔.
7. 구조층은 그림자를 드리우지 않음. 구조층은 별도 렌더링 레이어에 있어서 방 조명이 비추지 않음. 대신 단면에 약한 자체 발광을 주고, 드문드문 주황 경고등(구조층 레이어만 비춤)을 둠.

### 여기서 터진 것
- 단면 상자를 어둡게만 칠하면 구조층이 방 조명도 별빛도 못 받아서 우주 배경과 구분이 안 됨. 윤곽이 사라짐. 약한 자체 발광으로 해결함.
- 단면 상자가 처음에 전부 원점에 겹쳐 생겨서 소품만 떠 있는 것처럼 보였음(만들 때 위치를 안 줬음). 고침.
- 자체 발광을 처음에 세게 주니 단면이 "어두운 단면"이 아니라 밝은 회색 판으로 보였음. 리니어 색 공간이라 작은 발광 값도 화면에서는 꽤 밝게 나옴. 발광을 아주 약하게 줄임. 별빛은 원래 기본 레이어만 비추고 있어서 구조층 밝기와 무관했음(별빛 탓으로 의심했다가 확인 후 아님).

### 조절 가능한 것
- 카메라 쪽 단면 높이: 낮을수록 가장자리 방을 덜 가리지만 납작해짐.
- 반대쪽 단면 높이: 높을수록 벽 뒤 부피감이 커짐.
- 역할별 단면 색과 자체 발광 세기: 어두울수록 방이 도드라지고, 밝을수록 기계 윤곽이 읽힘.
- 경고등을 둘 확률과 색.

## 6. 소품(greeble) 채움

### 문제
단면 상자만으로는 "어두운 벽"이지 "기계로 꽉 찬 구역"이 아님. 손으로 놓으면 배가 바뀔 때마다 다시 해야 하고, 무작위면 불러올 때마다 달라짐.

### 후보
- 소품 계열: Data의 녹슨 사실풍 소품, Polyworks 단색 아틀라스 로우폴리, SciFiProps, Modular Pack의 기계.
- 배치 단위: 칸 하나씩 / 배 전체 한 번에 / 2×2칸 고정 묶음.

### 선택과 이유
- **Polyworks 한 계열로 통일.** 전부 아틀라스 텍스처 한 장과 재질 하나를 같이 써서 복사본 재질도 하나뿐이고, 같은 재질이라 SRP Batcher로 잘 묶임. 깎인 면이 형상으로 있는 로우폴리라 "깎은 중간 폴리곤" 목표와 가장 가까움. 녹슨 사실풍(Data)과 섞으면 그림체가 둘로 갈라짐.
- 2×2칸 고정 묶음: 묶음 경계가 고정이라 거주 칸이 바뀌어도 바뀐 근처 묶음만 다시 정해짐.

### 구현 방식
1. 소품 풀 에셋에 소품마다 층(납작/큼), 차지 칸(1×1 또는 2×2), 어울리는 역할, 가중치, 미리 잰 크기와 중심을 적어 둠.
2. 구조 칸을 2×2칸 고정 격자로 묶음.
3. 네 칸이 다 찬 묶음: 납작한 2×2 소품(배관 판, 환기구, 팬, 보강재) 하나는 항상 깔고, 역할별 확률로 큰 2×2 소품(탱크, 엔진 부품, 배관 교차, 피스톤) 하나를 더 올림.
4. 덜 찬 묶음: 칸마다 1×1 소품.
5. 고르는 값은 전부 "배 시드 + 묶음 좌표 + 용도 번호"의 해시라 같은 배면 같은 배치.
6. 소품은 칸 규격과 층별 최대 높이에 맞게 줄여서 칸 가운데 놓고, 90도 단위로 돌림.
7. 카메라 쪽 칸이면 납작한 소품만, 반대쪽 칸이면 큰 소품이 있을 때 큰 소품만 보임.
8. 원본 `Assets/Imports/`는 건드리지 않음. 쓸 프리팹, 메시, 아틀라스 텍스처를 프로젝트 폴더로 복사하고, 재질은 URP Lit으로 새로 만들어 아틀라스를 알베도에 연결함(원본 재질은 2D 셰이더로 잘못 변환돼 있어서 쓰지 않음). 복사본 프리팹의 충돌체는 지움(보기용).

### 여기서 터진 것
- 원본 재질이 2D 셰이더라 그대로 복사하면 3D에서 엉뚱하게 보임. 재질은 복사하지 않고 새로 만듦. Polyworks 아틀라스에는 노멀, 메탈릭, 오클루전, 발광 맵이 없어서 알베도만 연결함.
- 원본 프리팹을 그대로 복사하면 메시는 여전히 Imports 안의 FBX를 가리킴. 메시를 별도 에셋으로 복사하고 복사본 프리팹이 그것을 가리키게 바꿈. 복사본이 Imports를 하나도 참조하지 않는 것을 의존성 검사로 확인함.

### 조절 가능한 것
- 소품마다 가중치, 역할, 층, 차지 칸.
- 납작한 소품 최대 높이: 카메라 쪽 칸이 가장자리 방을 가리는 정도.
- 큰 소품 최대 높이: 반대쪽 칸의 부피감.
- 역할별 큰 소품을 올릴 확률: 낮추면 반대쪽도 납작해짐.

## 7. 실행 순서와 씬 구성

### 문제
컨트롤러는 시작할 때 바닥과 벽 그룹을 읽고, 변 편집기는 그다음 프레임 시작에 방 사이 벽을 넘겨받음. 생성이 그보다 늦으면 빈 그룹을 읽음.

### 구현 방식
1. 생성기 → 구조층 표현 → 컨트롤러 → 변 편집기 순으로 실행 순서를 고정함.
2. 생성기는 그룹 안의 이전 결과를 즉시 지우고 새로 만듦(지연 삭제를 쓰면 같은 프레임의 컨트롤러가 옛것과 새것을 둘 다 읽음).
3. 씬 구성: `Ship` 아래 바닥, 방 경계 벽, 가구, 방 조명, 외피, 구조층 그룹. 카메라 리그, 플레이어, 별빛, 외부 궤도 카메라는 확대판 시안 씬에서 그대로 가져옴. 외부 궤도 카메라의 중심은 생성기가 선체 가운데로 옮김.

### 여기서 터진 것
- 이 프로젝트는 Play 진입 때 도메인 리로드를 끔. 정적 값은 쓰지 않았음.
- 작업 중 Play 상태에서 에디터가 한 번 통째로 꺼짐(크래시 덤프만 남음). 원인은 모름. 다시 켠 뒤 같은 절차를 반복했을 때는 재현되지 않음.
- 외피 조각이 칸마다 하나씩이라 뚜껑을 닫은 화면의 그리기 호출이 많음(SRP Batcher로 거의 다 묶이긴 함). 묶음 단위 메시 합치기는 아직 안 함.

## 8. 확인 방법 (다시 해 볼 때)

- 결정론: 같은 입력으로 자동 채움을 두 번, 거주 칸 순서를 섞어서 한 번 더 돌려 비교값이 같은지 봄. 소품은 Play 중에 생성을 한 번 더 돌려 소품 이름, 위치, 방향의 해시가 같은지 봄.
- 변 편집기 회귀: Play 후 변 편집기가 읽은 벽, 문, 방 수가 확대판 시안과 같은지 봄.
- 내부 뷰: Q/E 네 방향 모두 찍어서 가장자리 방이 보이는지 눈으로 봄.
- 비용: Play 중 에디터 통계의 그리기 호출, SRP Batcher 호출, 삼각형 수를 뚜껑 열림/닫힘으로 비교.
