# 스토리 수직 슬라이스 프로토타입 계획서 ("조건 충족" 한 줄기)

> **계획서일 뿐이고 아직 코드, 씬, 프리팹은 하나도 바꾸지 않았음. 사용자 승인 전에는 구현하지 않음.**
> 작성 2026-11-24, 같은 날 사용자 검토 반영. 버릴 프로토타입임. 느낌을 잡은 뒤 본 구현은 새로 만듦. 그래서 하드코딩이 기본이고, 정하지 않은 규칙은 "미정, 출발값"으로 둠.

## 0. 한눈에

- **목적**: 한 사이클(깨어남 → 걸어서 징후 확인 → 길 고르기와 예약 → 시간 흐름 → 동면 → 기상과 결과)을 처음부터 끝까지 한 번 지나가 보고, 이 흐름이 게임이 되는지 눈으로 판정함.
- **이야기**: `QuestSeeds/05_Objects.md`의 씨앗 "조건 충족" 하나. 얼린 배아와 기르는 기계를 실은 씨앗선이 내 배에 붙었고, 기계가 내 배를 "조건 충족"으로 판정해 깨우기를 시작한 상황.
- **한 사이클 (플레이어가 겪는 순서)**

| 순서 | 플레이어가 하는 일 | 화면 |
|---|---|---|
| 1 깨어남 | 기상 요약 한 장을 읽음. 첫 줄은 씨앗 징후 문장("도킹한 뒤 재배 베이의 물 사용량이 오른다") | 요약 카드 |
| 2 징후 확인 | 배를 걸어 다니며 재배 베이의 물 사용량 눈금, 에어록 앞 상자 줄과 온도 눈금을 봄. 가까이 가야만 보임 | 내부 뷰(기존 WASD) |
| 3 길 고르기 | 모듈 길(함교에 장거리 스캐너 설치 예약) 또는 소지품 길(악기 + 고향의 녹음 넘기기) 중 하나를 고르거나, 아무것도 안 함(방치) | 예약 패널, 장소 상호작용 |
| 4 시간 흐름 | 드론이 설치하는 동안 걷거나 숙소에서 잠. 시계가 흐르면 피곤이 쌓이고, 자면 줄어듦. 상자 온도 눈금이 일정 시간마다 한 칸씩 오르는 것을 두세 칸 봄 | 내부 뷰 + 시계 + 피곤 게이지 |
| 5 동면 | 동면 포드에서 잠. 검은 화면에 가로로 긴 연도 바, 이벤트가 하나씩 나타났다 사라짐 | 동면 화면 |
| 6 기상과 결과 | 같은 연도 바에 표식이 남은 기상 요약을 읽고, 걸어가서 결과를 봄 | 요약 + 내부 뷰 |

- **사용자가 내릴 한 단어 판정 네 가지**

| 기호 | 질문 | 답이 나오는 단계 |
|---|---|---|
| (가) | 걸어서 확인하는 일이 일 같은가 | 2, 3 |
| (나) | 예약하고 기다리는 시간이 지루한가 | 1, 3 |
| (다) | 연도 바가 연출로 좋은가 | 4 |
| (라) | 방치 결과가 아프게 읽히는가 | 5 |

### 0.1 정해진 것 (사용자 결정 2026-11-24, `GameConcept.md` 18장 [확정]과 같음)

| 결정 | 이 프로토타입에서의 뜻 |
|---|---|
| 드론에게 설치를 맡겨 배정이 끝났으면, 내가 동면에 들어가도 설치는 끝나고 모듈은 동작함 | 스캐너 설치를 예약만 하고 자도 기상 뒤 스캐너는 설치돼 있음 |
| 내가 직접 해야 하는 일을 안 했으면 그대로 남음. 아무 일도 안 일어남 | 스캔, 좌표 넘기기, 악기와 녹음 넘기기는 내 손이 필요하므로, 안 하고 자면 그 길은 없던 일이 됨 |
| 시계는 초 단위 숫자만 보여 주고 흐르기만 함. 일차, 날짜, "하루"라는 단위는 없음. 정해진 수면 시간도 없음 | 화면에는 경과 초 하나만 뜸 |
| 시계가 흐르면 피곤(수면욕구)이 쌓이고, 동면이 아닌 잠을 자면 피곤이 줄어듦 | 피곤 게이지 하나를 만듦. 무드와 몸 상태는 만들지 않음 |
| 선체 공간은 나중에 네 가지로 나뉨((1) 걸어 다닐 수 있는 내부 (2) 걸어 다닐 수 없는 내부 (3) 모듈을 못 붙이는 외부 (4) 모듈을 붙일 수 있는 외부) | 프로토타입은 (1)만 씀. 스캐너는 (1)의 함교에 둠 |
| 씨앗과 문서의 "하루", "며칠", "한 사이클"은 이야기 속 표현이고 게임에서는 시계 위의 시간 길이 상수로 옮김(18장 제안 8번) | 씨앗의 "하루에 한 칸"은 **"시계 N초마다 한 칸"(N은 출발값)**으로 옮김. 씨앗 문장 자체는 고치지 않음 |

## 1. 지금 있는 것 (파일을 읽어서 확인한 것만)

| 항목 | 상태 | 근거 |
|---|---|---|
| 캐릭터가 걷는 기능 | **있음**. CharacterController를 WASD로 화면 기준 이동, 중력 처리 | `ShipBlockoutController.cs` 읽음 |
| 뷰 전환 | **있음**. Tab으로 뚜껑(외피·지붕) 열고 닫기, 내부 카메라와 궤도 카메라 즉시 컷 전환, Q/E 90도 회전, 휠 줌 | 같은 파일 |
| 방 개념 (데이터) | **있음, 단 칸막이 도구 안에서만**. 변 데이터에서 flood fill로 방을 계산하고 도달 가능 검사를 함 | `ShipEdgeGrid.cs`에 방 계산과 도달 검사 함수 있음 |
| 방 개념 (씬) | **이름으로만 있음**. `ShipBlockout_Large`에 바닥 그룹 `Floor_Workshop`, `Floor_WindowNook`, `Floor_Storage`, `Floor_Quarters`, `Floor_Lab`, `Floor_Kitchen`, `Floor_HibernationRoom`, `Floor_DroneHangar`, `Floor_Corridor`, `Floor_Bridge`가 있음 | 씬 파일의 오브젝트 이름 확인 |
| 쓸 만한 가구 | `HibernationPod`, `PodMonitor`, `PilotSeat`, `HangarHatch`, `HangarCrate`, `QuartersShelf`, `Plant_1~3`, `LifeSupport_1~2` 등 | 같은 씬 |
| 화면 글자 | 기존 컨트롤러가 OnGUI(즉석 GUI)로 한국어 버튼과 도움말을 띄움. UI 패키지(ugui)는 설치됨 | 컨트롤러, `Packages/manifest.json` |
| 입력 | Input System 전용 | 컨트롤러가 Keyboard.current를 직접 읽음 |
| 이미 쓰는 키 | Tab, WASD, Q, E, 휠, 우클릭 드래그(컨트롤러). B, 1, 2, 3, V, 클릭(칸막이 도구, 문서 13.2절 기준) | 컨트롤러 코드, `ShipBuildDesign.md` 13.2절 |
| 이동 속도 | 컨트롤러의 공개 값 하나로 정해짐. 바꾸려면 컨트롤러 형식을 코드에서 불러야 함 | 컨트롤러 코드 |
| 컨트롤러의 커밋 전 수정 | 다른 세션이 화면 방향 읽기 속성과 "뷰 바뀜" 알림을 추가함(9줄 추가, 2줄 변경). 걷기와 뷰 전환 동작은 그대로 | `git diff` |
| `Scripts/ShipBlockout/` | 스크립트가 4개가 아니라 11개임. 커밋된 4개(컨트롤러, 선체 생성기, 변 격자, 변 편집기) + 다른 세션이 새로 만든 7개(구조층) | 폴더 목록, `git status` |
| asmdef | 저장소(Imports 제외)에 없음. 전부 기본 어셈블리 | 파일 검색 |

**확인 못 한 것**

- 재배 베이와 에어록: `ShipBlockout_Large`에 그 이름의 방이 **없음**. `Plant_1~3`이 어느 방에 있는지는 확인 못 함. 에어록 대역 후보는 `Floor_DroneHangar`의 `HangarHatch`인데 실제 위치가 맞는지 확인 못 함.
- 숙소에 침대 오브젝트가 있는지: 이름으로 찾은 것은 `QuartersShelf`뿐임. 침대가 없으면 숙소 바닥에 잠자는 지점 표식만 둠.
- OnGUI 한국어가 화면에서 깨지지 않고 나오는지: 코드상 쓰고 있다는 것만 확인함. Play해서 보지 않았음.
- `ShipBlockout.unity`(첫 시안): 카메라와 컨트롤러가 없다고 문서에 적혀 있음. 씬 파일에서 컨트롤러 스크립트 참조를 따로 확인하지 않았음. 이 계획은 이 씬을 쓰지 않음.
- 씬과 프리팹을 Unity 에디터로 열어 보지 않았음. 전부 텍스트 파일로만 읽음.

## 2. 만드는 것과 하지 않는 것

**만드는 것**

| 무엇 | 한 줄 설명 |
|---|---|
| 프로토타입 씬 | `ShipBlockout_Large`를 복사한 새 씬. 원본은 안 건드림 |
| 게임 시계 | 경과 초 하나. 평소엔 실제 시간과 같이 흐르고, 잠자는 동안만 빨리 흐름 |
| 피곤 게이지 | 시계가 흐르면 쌓이고 잠자면 줄어듦. 높으면 불이익 하나(임시) |
| 씨앗 상태 하나 | 상자 온도 눈금, 물 사용량, 고른 길, 설치 진척. 전부 하드코딩한 한 덩어리 |
| 장소 표식 | 배의 특정 지점에 붙은 징후. 가까이 가야 글과 눈금이 보이고, 상호작용 키로 씀 |
| 예약 패널 | 함교 장거리 스캐너 설치 예약 한 가지만 있는 임시 패널. 월드에 놓지 않음 |
| 동면 화면 | 검은 화면, 연도 바, 하나씩 나타났다 사라지는 이벤트 3~5개 |
| 기상 요약 | 시작할 때는 카드 한 장, 동면 뒤에는 연도 바에 표식이 남은 형태 |
| 결과 연출 | 갈래마다 달라지는 배 안의 모습(상자 유무, 벽 눈금, 물 눈금, 스캐너 유무) |

| 무엇 | 이유 |
|---|---|

| 저장과 불러오기 | 한 사이클을 한 번에 지나가므로 필요 없음 |
| 테스트 먼저 쓰기 | 판정 대상이 재미와 연출이라 자동 테스트로 답이 안 나옴 |
| 선외 활동 | 설계 결정 8번. 선외 작업은 드론이 함. 이번 길은 전부 (1) 걸어 다닐 수 있는 내부에서 끝남 |
| 사이오닉, 교역 | 이 씨앗의 두 길에 필요 없음 |
| 무드와 몸 상태 | 피곤 게이지 하나만 만듦. 나머지는 판정 네 가지에 필요 없고 넣으면 판정이 흐려짐 |
| 오락으로 시간 당기기 | 18장 [확정]에 있지만 이번 판정에 필요 없음. 가속은 잠 하나로 봄 |
| 여러 씨앗 | 한 이야기만 지나감 |
| 씨앗의 나머지 세 길(함선 AI, 프로그래밍 가능한 물질, 옛 포드)과 맨손 | 모듈 길 하나, 소지품 길 하나면 "예약"과 "가서 씀"을 둘 다 봄 |
| 진짜 배치 패널(평면도, 놓을 수 있는 칸 표시) | `ShipBuildDesign.md` 0.5절대로 설계가 아직 없음. 버튼 몇 개로 대신함 |
| 선체 공간 네 가지 구분 | 프로토타입은 (1)만 씀. 나머지는 분류만 정해졌고 어느 모듈이 어디 가는지 미정 |
| 모듈의 실제 3D 배치와 선체 재생성 | 구조층 작업 영역과 겹침. 설치 진척은 함교의 기존 오브젝트 옆 표식으로만 보임 |
| 동면 중 깨우는 사건(바 멈춤) | 18장 제안 3번이라 아직 확정 아님. 열린 질문 5번 |

## 3. 단계

각 단계가 끝나면 Unity에서 Play해서 눈으로 볼 수 있는 결과가 나옴. 단계마다 Play 후 콘솔 오류 0개를 확인하고 사용자에게 판정을 받음.

### 단계 1: 프로토타입 씬, 시계, 피곤, 잠

| 칸 | 내용 |
|---|---|
| 만드는 파일 | 새 씬(가칭 `Assets/Scenes/Prototype_SeedShip.unity`, `ShipBlockout_Large` 복사본), 시계 스크립트, 피곤 스크립트. 숙소에 잠자는 지점 표식 |
| 하드코딩 | 시계는 0초에서 시작. 평소 배율 1(실제 1초 = 시계 1초). 잠자는 동안 시계 배율(출발값). 피곤이 쌓이는 속도, 잠이 피곤을 줄이는 속도, 피곤 불이익 하나(임시: 상호작용에 드는 시계 시간이 늘어남. 열린 질문 6번) |
| 사용자가 볼 것 | 화면 구석에 "경과 N초" 하나와 피곤 게이지. 걷는 동안 초가 흐르고 피곤이 차오름. 숙소 지점에서 상호작용하면 잠들고, 그동안 화면이 어두워지며 초가 빠르게 넘어가고 피곤이 내려감. 피곤이 바닥나거나 상호작용 키를 다시 누르면 깸 |
| 답이 나오는 판정 | (나) 일부: 시계가 흐르는 빠르기, 그리고 피곤 때문에 자러 가는 일이 지루한지 |
| 끝 조건 | 기존 Tab, WASD, Q/E가 원본 씬과 똑같이 동작함. 새 키가 기존 키와 겹치지 않음. 일차, 날짜, 시각 표시가 어디에도 없음 |

### 단계 2: 기상 요약 카드와 걸어서 보는 징후

| 칸 | 내용 |
|---|---|
| 만드는 파일 | 씨앗 상태 스크립트, 장소 표식 스크립트, 기상 요약 스크립트. 씬에 표식 지점용 빈 오브젝트와 상자 줄(기본 도형) 추가 |
| 하드코딩 | 요약 첫 줄은 씨앗 징후 문장. 재배 베이 대역 지점(화분 근처)의 물 사용량 눈금. 에어록 대역 지점(격납고 해치 앞)의 상자 줄과 줄마다 온도 눈금. 첫 줄은 이미 "되얼릴 수 없는 칸"을 넘은 상태. 온도 눈금은 시계 N초마다 한 칸, 물 눈금도 같은 간격으로 오름 |
| 사용자가 볼 것 | 시작하면 요약 카드 한 장. 닫고 걸어가면 화분 근처에서만 물 눈금이, 해치 앞에서만 상자와 온도 눈금이 보임. 시계가 한 칸 간격만큼 흐를 때마다 온도 눈금이 한 칸 오르고 물 눈금도 오름. 한 번 자고 오면 몇 칸 오른 게 보임 |
| 답이 나오는 판정 | (가): 징후를 보러 걷는 일이 일 같은지, 장소를 찾아가는 재미가 있는지 |
| 끝 조건 | 징후는 멀리서 안 보이고 가까이서만 보임. 한 칸 간격의 두 배를 넘기면 상자 눈금이 두 칸 오른 게 보임 |

### 단계 3: 두 길과 예약

**고른 길 (씨앗을 읽고 제안함)**

| 길 | 씨앗 원문 요지 | 고른 이유 | 프로토타입 흐름 |
|---|---|---|---|
| 모듈 길: [장거리 스캐너] 진짜 맞는 곳을 대 준다 | 지나온 좌표 중 물과 볕이 있던 곳을 스캐너로 다시 보고 좌표를 기계에 넘김 → 씨앗선이 떠남 | "예약 → 드론이 설치 → 내가 가서 쓴다"가 다 들어감. 드론이 하는 몫과 내 손이 하는 몫이 갈려서, 예약만 하고 잤을 때의 결과도 따로 보임 | 예약 패널에서 함교 스캐너 설치 예약 → 드론 배정 → 드론이 설치(진행률이 시계와 함께 오름) → 완료되면 함교 조종석에서 내가 스캔(시계 시간이 듦) → 해치 앞 기계에 내가 좌표 넘김 |
| 소지품 길: [악기 + 고향의 녹음] 가르칠 것을 넘긴다 | 녹음과 내가 친 가락을 넘김 → 기계가 "더 모아야 한다"고 판정, 깨우기가 한 사이클 미뤄짐 | 설치 없이 내 손으로 "가서 집고, 가서 넘김"만 있는 길이라 모듈 길과 비교가 됨. 결과가 해결이 아니라 미룸이라 동면 뒤에 문제가 남아 있는 모습을 봄 | 숙소 선반에서 악기와 녹음을 집음 → 해치 앞 기계에 넘김(가락을 치는 데 시계 시간이 듦) |

| 칸 | 내용 |
|---|---|
| 만드는 파일 | 예약 패널 스크립트. 씨앗 상태와 장소 표식에 길 진행 추가 |
| 하드코딩 | 패널 항목은 "장거리 스캐너 설치(함교)" 하나. 설치 주체는 드론 고정이고 화면에는 "드론 배정됨, 설치 중"으로 씀. 설치 시간, 스캔 시간, 가락 치는 시간(모두 시계 초). 길은 하나만 고를 수 있음(다른 길을 고르면 앞 길은 취소) |
| 사용자가 볼 것 | 패널을 열어 예약하면 함교 표식에 "설치 중 N%"가 오름. 걸어 다니거나 자면서 기다림. 완료 뒤 함교에서 스캔하고 해치로 가서 넘김. 소지품 길은 숙소와 해치를 오가며 끝남 |
| 답이 나오는 판정 | (나): 설치가 끝나기까지 기다리는 시간(잠 한두 번 분량)이 지루한지. (가): 함교와 해치를 오가는 일이 일 같은지 |
| 끝 조건 | 두 길 모두 끝까지 지나감. 아무 길도 안 고르고 동면에 들어갈 수 있음(방치). 예약만 하고 설치가 끝나기 전, 또는 설치 뒤 스캔 전에 동면에 들어갈 수 있음(예약만 하고 동면) |

| 평소 배율 1이라 깨어 있는 시간이 길고, 잠 말고는 시간을 당길 수단이 없음 | 의도된 관찰 대상임. 한 판 길이는 피곤 쌓이는 속도, 설치 시간, 이벤트 간격으로 맞춤(열린 질문 7번). 그래도 길면 판정 (나)의 답으로 받음 |
| 피곤이 너무 빨리 차서 걷다가 계속 자러 가야 함, 또는 너무 느려서 잠이 의미가 없음 | 상수 두 개(쌓이는 속도, 줄이는 양)로 조절. 판정 (나)를 받으며 고침 |
| 설치를 기다리는 동안 할 일이 없음 | 의도된 관찰 대상임. 판정 (나)가 "지루하다"면 그것이 답. 프로토타입이 일부러 메우지 않음 |
| "예약만 하고 동면"이 방치와 같아서 예약이 헛수고처럼 읽힘 | 정해진 규칙(내 손이 필요한 일은 안 하면 그대로)을 그대로 보여 주는 것이 목적. 함교 표식 한 줄로 "설치는 됐다"를 보여 주고, 아프게 읽히는지 판정 (라)로 같이 받음 |
| 방치 결과가 글로만 읽혀서 안 아픔 | 요약에서 다 말하지 않고 걸어가서 벽 눈금을 보게 함. 열린 질문 4번 |
| 하드코딩이 커져서 버리기 아까워짐 | 스크립트 7개, 새 폴더 하나로 묶음. 다른 코드가 이 폴더를 참조하지 않음. 지울 때 폴더와 씬만 지우면 됨 |
| 컨트롤러를 끈 동안 카메라 따라가기도 멈춤 | 동면 화면은 검은 화면이라 상관없음. 잠잘 때도 화면을 어둡게 해서 가림. 깬 뒤 다시 켬 |

## 9. 열린 질문 (사용자가 정할 것)

설치가 끝나기 전에 동면하면 어떻게 되나는 **정해짐**(0.1절: 드론 설치는 끝나고 동작함, 내 손이 필요한 일은 그대로 남음). 질문에서 뺌.

1. **두 길을 장거리 스캐너와 악기 + 녹음으로 해도 되나?** 추천: 그대로. 스캐너는 "예약 → 드론 설치 → 내가 가서 씀"을, 악기는 "내 손으로만, 해결이 아니라 미룸"을 보여 줘서 서로 다름.
2. **동면 길이를 플레이어가 고르게 할까, 하나로 고정할까?** 추천: 고정. 이번엔 연도 바 연출(다) 판정에 집중하고, 고르기는 다음 프로토타입에서.
3. **자는 동안 시계 배율을 얼마로 시작할까?** 가정: 시계는 초 표시만 하고, 평소엔 실제 1초 = 시계 1초, 잠과 오락만 가속함(프로토타입은 잠만). 추천: 잠 배율을 크게 잡아 잠 한 번이 실제 수십 초 안에 끝나게 시작하고, 판정 (나)를 보며 줄임.
4. **방치 결과를 기상 요약에 글로 다 쓸까, 걸어가서 보게 할까?** 추천: 요약에는 "에어록 앞 이상 감지" 한 줄만, 키 눈금과 바닥난 물은 걸어가서 보게 함. 판정 (라)와 (가)를 같이 받음.
5. **동면 중 나를 깨우는 사건(바가 멈춤)을 이번에 넣을까?** 추천: 넣지 않음. 18장에서 아직 제안이고, 이 씨앗의 방치는 "자는 동안 진행되는 일"이라 깨우면 결과가 달라짐.
6. **피곤이 높을 때의 불이익을 무엇 하나로 할까?** 임시 제안은 "상호작용(스캔, 가락 치기 등)에 드는 시계 시간이 늘어남". 컨셉 5장의 "조작에 시간이 더 걸린다"와 같고, 기존 컨트롤러를 안 건드려도 됨. 다른 안 "이동이 느려짐"은 눈에 더 잘 보이지만 컨트롤러 형식을 코드에서 불러야 해서 구조층의 asmdef 작업과 엮임(충돌 위험 3번). 추천: 상호작용 시간 증가.
7. **한 판(한 사이클)을 얼마 안에 끝내게 할까?** 시계 단위가 초뿐이고 평소 배율이 1이므로, 한 판 길이는 피곤이 쌓이는 속도(몇 번 자야 하나), 스캐너 설치 시간, 상자 눈금 간격, 동면 바와 이벤트 간격으로 정해짐. 추천: 한 판 15분 안팎을 목표로 먼저 못 박고, 이 값들을 거기서 거꾸로 맞춤. 네 갈래를 다 봐도 한 시간 안쪽이 됨.

## 10. 우주선 연동 (2026-11-24 대화로 추가)

우주선 계획 세션이 만드는 배(`Docs/ShipLayoutNetworkPlan.md`, 통로 그물)와 이 프로토타입을 어떻게 잇는지 정한 것과 구상임.

**확정**
- 프로토타입은 **우주선 1b 판정 뒤에** 새 배 위로 옮긴다. 그때까지는 `ShipBlockout_Large` 복사본 위에서 돈다(사용자 결정).
- 지금 얻는 판정 (나), (다), (라)는 배 모양에 거의 기대지 않는다. (가) "걸어서 확인하는 일이 일 같은가"는 옛 배 기준이라, 새 배로 옮긴 뒤에 다시 받는다.
- 우주선 쪽 작업은 새 하위 세션이 이어받아 본부(이 세션)에 보고한다. 에디터는 한 번에 한 세션만 쓰고, 쓰기 전에 서로 한 줄로 알린다.

**구상 (옮길 때 적용, 아직 정하지 않음)**
- 장소는 좌표가 아니라 **모듈 이름으로 조회**한다. 우주선 쪽의 "임시 모듈 이름"(재배 베이, 에어락, 함교, 숙소, 동면실)을 1b 시안의 자리에 걸어 달라고 요청한다. 방 위치는 계속 바뀌므로 좌표를 하드코딩하지 않는다.
- 예약은 자리 상태와 이어진다: 빈 자리(줄무늬) → 설치 중 → 놓임. 지금의 임시 예약 패널과 설치 진행 표식은 그쪽 패널과 자리 표시로 대체된다.
- 인터페이스는 데이터다. 새 배 데이터를 읽는 질의(자리 이름, 칸 좌표, 문 칸)만 쓰고 코드 형식 이름은 직접 부르지 않는다. asmdef는 우주선 1b에서 들어오며, 그때 `Assets/Scripts/Prototype/`에서 참조를 한 번 추가한다.
- 격벽 도어락과 구획(1b)은 공기, 불, 진공 같은 사건의 무대가 될 수 있다. 이번 프로토타입에는 넣지 않는다.
- 용어는 우주선 쪽 확정 용어를 쓴다: **블록**(선체 덩어리, 옛 이름 세그먼트), **가압구역**(걷는 영역: 통로 칸 + 방칸), **설비구역**(못 걷는 내부). 장소(재배 베이, 에어락, 함교, 숙소, 동면실)는 가압구역의 방이다. **모듈은 걸음을 막으므로(사용자 결정, N×M 칸 단위) 방 사이 이동 시간이 배치에 따라 바뀔 수 있다.** 새 배로 옮긴 뒤 걷기 판정 (가)는 이 영향까지 포함해서 받는다.

## 11. 웹 이벤트 엔진 연동 (2026-11-24 대화로 추가, 제안)

사용자 말: 웹 게임이 이벤트 처리를 맡으니, **지금 플레이어의 동작(걷기, F 상호작용, 예약, 동면) 위에 웹의 이벤트 처리가 들어간다.** 유니티 작업도 거기에 맞춘다. 웹 쪽 계획은 [SeedGamePlan.md](SeedGamePlan.md)이고 1단계만 승인됐다.

**유니티가 웹에서 받는 것(제안)**
- 사건 데이터: 조건(시기와 가진 것), **공개 단계**(표면 → 일반 검토 → 능력 검토 → 깊은 검토), 길의 요구와 효과, 방치 결과, 후속. 웹의 내보내기 JSON이 원본이고 유니티는 읽기만 한다.
- 규칙은 웹이 먼저 검증한다. 유니티에서 새 규칙을 먼저 만들지 않는다(자원, 함교 같은 새 게임플레이 보류 원칙 유지).

**플레이어 동작과의 대응**

| 유니티의 지금 동작 | 웹 이벤트 엔진에서의 뜻 |
|---|---|
| 걸어가 장소 표식을 봄, F | 징후(표면)를 봄, "검토한다" 선택 |
| 검토 결과 문장 | 공개 단계가 능력에 따라 정해짐(능력 없음이면 "겉으로는 잘 되어 있는 것 같다"에서 멈춤) |
| R 예약 패널과 설치 진행 | 능력 목록의 타이머(설치, 분석, 배양). 끝나기 전에는 가동 아님 |
| 시계(경과 초)와 피곤 | 시뮬레이션 시계. 동면이 정식 빨리감기 |
| 동면 포드와 연도 바 | 동면 길이 선택(상한은 동면 수단 단계), 사건이 하나씩 나타났다 사라짐, 깨움 |

**순서(제안)**
1. 웹 1단계(공짜 수리 한 장)와 3단계(시계, 타이머, 사건 두 갈래)가 사건 스키마 v0를 굳힌다. 이 사이 유니티는 코드를 키우지 않는다.
2. 유니티는 하드코딩된 "조건 충족" 슬라이스를 **스키마를 읽는 이벤트 러너**로 바꾼다. 씨앗 하나로 시작한다.
3. 장소는 우주선 쪽 모듈 이름 조회로 잇는다(10장).
4. 동면 길이 선택(연도 바에서 길이를 고름, 상한은 동면 장치 단계)은 별도 단계로 넣는다.

**유니티에 작게 먼저 할 수 있는 것**: 예약 패널이 길 목록을 처음부터 보이는 것이 정보 단계 공개 원칙(GameConcept 18장 제안 9)과 어긋난다. 웹 1단계 판정에서 단계 공개가 좋다고 나오면 이 프로토타입에 같은 방식으로 적용한다. 에디터 순서가 필요하다.
