# 구조층 도입 계획서 (구현 전, 사용자 승인 대기)

작성 2026-11-24. **계획서일 뿐이고 아직 코드, 씬, 프리팹은 하나도 바꾸지 않았음.** 사용자 승인 전에는 구현하지 않음.
이 문서에 나오는 수치(두께, 높이, 개수, 폴리 수)는 전부 **출발값**이고 프로토타입에서 눈으로 보고 고칠 값임.
관련 문서: `Docs/ShipBuildDesign.md` 0.1~0.4절, 13장. 이 계획은 그 문서의 0.x절 결정을 전제로 함.

## 0. 한눈에

- **문제**: 지금 외피는 거주 칸 바로 바깥을 얇게 한 겹 감쌈. 그래서 배의 윤곽이 방 배치를 그대로 따라가고, "호텔이 떠다니는 것 같다"는 판정을 받음. FTL의 배는 거주 공간이 가운데 일부이고, 나머지 대부분은 엔진, 탱크, 배관, 장갑 같은 기계 구역이며 윤곽은 그 기계 구역이 정함.
- **해결 방향(합의됨)**: 칸 종류를 셋으로 둠.
  - **거주 칸**: 사람이 걷고 모듈을 올리는 칸. 지금 있는 것.
  - **구조 칸**(신규): 거주 칸과 외피 사이를 채우는 비거주 볼륨. 거주 칸 둘레에 몇 칸 두께로 자동으로 채워지고, 엔진 포드나 탱크 돌출 같은 형태를 가짐. 플레이어는 못 들어가고 드론이 수리함.
  - **외피**: 지금 있는 조각 키트. 이제 거주 칸이 아니라 "거주 칸 + 구조 칸" 전체의 바깥을 감쌈.
- **보이는 것**: 외부 뷰(뚜껑 닫힘)에서는 외피가 구조층까지 덮어 윤곽이 방 모양과 분리됨. 내부 뷰(뚜껑 열림)에서는 방 바깥이 어두운 단면으로 기계가 꽉 찬 것처럼 보임.
- **단계**: 5단계. 각 단계마다 사용자가 Unity 화면으로 "예쁜가, 배처럼 읽히는가"를 판정할 수 있는 결과가 나옴. 첫 단계는 회색 상자로 구조 칸 두께만 채워서 윤곽이 달라지는지만 봄.

## 2. 지금 코드가 하는 일 (계획의 출발점)

이 절은 계획을 읽는 사람이 코드를 열지 않아도 되게 하려고 씀.

- **외피 생성기**(`ShipHullGenerator`): 인스펙터에 직접 적힌 "방 목록"(왼쪽 아래 칸, 크기, 창 여부, 지붕 덮개)과 "막힌 칸" 목록(엔진 자리 2×2칸 세 개)을 읽음. 방 칸마다 지붕과 밑판을 놓고, 이웃이 비어 있는 변마다 벽(또는 창 벽)을, 두 이웃이 모두 빈 꼭짓점마다 볼록 모서리를 놓음. 뱃머리, 용골, 함교 차양, 엔진은 "추가 부품" 목록에 **절대 좌표**로 적혀 있음. 에디터에서 컴포넌트 메뉴로 실행하면 `HullGenerated` 아래에 다시 만듦. 오목 모서리 조각은 없음(지금 배에는 오목 모서리가 없어서 필요가 없었음).
- **변 데이터**(`ShipEdgeGrid`): 거주 칸 집합과 칸 사이 변의 상태(없음, 벽, 문)를 가짐. 방은 저장하지 않고 벽으로 막힌 칸 덩어리를 계산함. 두 칸이 모두 거주 칸인 변만 편집할 수 있고, 우주와 맞닿은 변은 선체 소유라 저장하지 않음.
- **변 편집기**(`ShipEdgeEditor`): 시작할 때 `Floors` 그룹의 바닥 칸 위치로 거주 칸 집합을 만들고, 씬의 방 사이 벽을 변 데이터로 읽어 새 조각으로 바꿈. 저장은 없음.
- **컨트롤러**(`ShipBlockoutController`): 뚜껑을 열면 `Exterior` 아래 모든 렌더러를 "그림자만" 모드로 바꿔서 안 보이게 하되 빛은 계속 막음. 방 사이 벽은 전부, 바깥 벽의 안쪽 면은 카메라 쪽만 0.3m 높이 복제본으로 바꿔 낮춤. 카메라 방향은 시작이 45도이고 Q/E로 90도씩 돌아서 **항상 대각선**임. 그래서 네 변 중 두 변은 카메라 쪽, 두 변은 반대쪽으로 깔끔하게 나뉨. Play 동안 그림자 거리를 110m로 늘림(카메라가 70m 뒤에 있어서).
- **씬**(`ShipBlockout_Large`): 거주 칸 292칸, 방 10개, 엔진 자리 3개. 부착물(탱크 두 개, 방열판 네 개, 안테나, 접시 안테나)은 `Exterior` 바로 아래에 손으로 놓은 기본 도형이고 위치가 절대 좌표임.
- **테스트**: 저장소에 어셈블리 정의 파일(asmdef)과 테스트가 하나도 없음.

## 3. 데이터 모델

### 3.1 문제

구조 칸을 거주 칸과 섞지 않고 저장해야 함. 섞으면 변 편집기, 방 계산, 이동, 나중의 드론 길찾기가 구조 칸을 "걸을 수 있는 칸"으로 오해함. 동시에 구조 칸은 손상 상태를 가지므로 매번 버리고 새로 만드는 외피와 달리 **저장되는 데이터**여야 함. 그리고 거주 칸이 바뀌면 구조층이 따라 바뀌어야 함.

### 3.2 후보

1. **칸마다 종류 값을 하나 두고 한 집합에 넣기.** 거주 칸 집합을 "칸 → 종류" 사전으로 바꿈. 단순하지만 지금 변 데이터와 방 계산이 "집합에 있으면 걸을 수 있는 칸"으로 읽고 있어서 모든 호출부를 고쳐야 함.
2. **구조 칸을 별도 집합으로 두기.** 거주 칸 집합(지금 그대로)과 구조 칸 사전(칸 → 구조 칸 상태)을 나란히 둠. 외피 생성기만 둘을 합쳐 읽음.
3. **구조 칸을 아예 저장하지 않고 매번 계산하기.** 외피처럼 불러올 때 재생성. 손상 상태를 저장할 곳이 없어지므로 합의된 범위(드론 수리 대상, 손상 저장)와 맞지 않음.

### 3.3 선택과 이유

**2번(별도 집합)을 추천함.**
- 변 데이터와 방 계산은 거주 칸만 알면 되고, 구조 칸이 들어와도 손댈 필요가 없음. 우주와 맞닿은 변을 선체가 소유한다는 규칙이 "거주 칸과 구조 칸 사이 변도 선체 소유"로 자연스럽게 넓어짐(두 칸이 모두 거주 칸이어야 편집 가능하다는 지금 규칙 그대로).
- 구조 칸 상태가 거주 칸과 다른 속성(내구도, 역할, 나중의 배관/전력 자리)을 가지므로 따로 두는 쪽이 읽기 쉬움.
- 3번은 손상 저장과 충돌해서 탈락.

### 3.4 구조 칸 하나가 갖는 것

| 항목 | 의미 | 이번 범위 |
|---|---|---|
| 좌표 | 칸 위치. 지금은 한 층이라 평면 좌표. 0.x절이 말한 3차원 좌표로 갈 때 층 값을 더함 | 씀 |
| 역할 | 일반 채움 / 엔진 자리 / 탱크 / 장갑 / 배관 간선 후보 같은 분류. 윤곽 형판이 정함. greeble 고르기와 나중의 기능에 씀 | 씀 |
| 출처 | 기본 두께로 생긴 칸인지, 어느 윤곽 형판이 찍은 칸인지 | 씀 |
| 내구도 | 손상 정도. 가득 참이 기본 | 씀 |
| 배관 망 번호, 전력 망 번호 | 나중에 배관과 전력 규칙을 붙일 자리. 비워 둠 | **자리만** |
| 시대 | 이 칸이 만들어진 시대(6장 원칙: 태어난 시대 유지) | 자리만 |

### 3.5 저장하는 것과 다시 만드는 것

- **저장**: 거주 칸 목록, 변 상태, 모듈 배치(기존 원칙), 그리고 **구조 칸 목록과 각 칸의 역할, 출처, 내구도**. 내구도는 가득 찬 칸은 빼고 손상된 칸만 적는 희소 기록이면 충분함.
- **다시 만듦**: 외피 조각, 벽 조각, 구조층의 블록아웃 상자와 greeble 소품, 수리 지점 위치. 전부 저장된 칸 데이터에서 결정론적으로 나옴.
- **왜 구조 칸 목록 자체를 저장하는가**: 자동 채움 규칙(두께, 형판)을 나중에 고쳐도 이미 있는 세이브의 배 모양이 갑자기 바뀌지 않게 하려는 것. 자동 채움은 "거주 칸이 바뀔 때 구조 칸 목록을 새로 써 주는 도구"이고, 불러오기 때는 실행하지 않음. 이건 사용자 확인이 필요한 결정이라 열린 질문에도 올림(10절 1번).

### 3.6 자동 채움 규칙 (거주 칸이 바뀔 때)

순서대로 실행함. 각 단계는 **조절 가능한 노브**를 가짐.

1. **기본 띠**: 거주 칸에서 일정 거리 안의 빈 칸을 전부 구조 칸으로 만듦. 거리를 재는 방식에 따라 모서리 모양이 달라짐. 가로세로 거리 합으로 재면 모서리가 비스듬히 깎이고, 큰 쪽 거리로 재면 네모난 모서리가 됨. 출발값은 두께 2칸, 깎인 모서리.
2. **움푹한 곳 메우기**: 방 배치 때문에 생긴 좁은 홈과 안쪽 구멍을 메움(넓혔다가 다시 좁히는 형태 연산, "닫기"라고 부름). **이 단계가 윤곽을 방 모양에서 떼어 내는 핵심임.** 메울 홈의 최대 폭이 노브임.
3. **창 면 예외**: 창이 필요한 방의 바깥 면(함교 앞, 창가 방)은 그 방향으로 구조 칸을 채우지 않음. 이렇게 안 하면 구조층이 모든 창을 덮어 버림. 2단계가 이 틈을 다시 메우지 않도록 창 면 앞은 "채우기 금지 칸"으로 먼저 표시해 둠.
4. **윤곽 형판 찍기**: 데이터로 정의한 형판(엔진 포드, 탱크 돌출, 용골, 등줄기, 날개 모양 방열판 받침 등)을 정해진 기준점에 찍어 구조 칸을 더함. 기준점은 "가장 뒤쪽 열", "배 중심선", "아래쪽 가장자리"처럼 거주 칸 배치에서 계산되는 위치로 정함. 형판은 기본 두께 상한(4칸)을 넘을 수 있음. 엔진 포드가 배 뒤로 길게 튀어나오는 것이 이 단계임.
5. **대칭**: 켜면 배 길이 방향 중심선 기준으로 구조 칸을 거울 복사함. FTL 배 대부분이 좌우 대칭이라 윤곽이 배처럼 읽히는 데 크게 기여할 것으로 봄. 거주 칸은 대칭이 아니어도 됨.
6. **기존 칸 이어받기**: 새로 계산된 구조 칸 중 이전에도 있던 칸은 내구도와 시대를 그대로 이어받음. 새로 생긴 칸은 내구도 가득. 사라진 칸의 손상은 버려짐(손상을 버려도 되는지는 열린 질문 10절 2번).
7. **충돌 규칙**: 거주 칸이 구조 칸 자리로 확장되면 그 칸은 거주 칸이 이김(구조 칸에서 빠짐). 엔진 자리 역할을 가진 칸은 거주 칸 확장을 막을지, 같이 밀려날지 정해야 함(열린 질문 10절 4번).

### 3.7 결정론

- **같은 입력이면 같은 결과**여야 함. 입력은 거주 칸 집합, 창 면 표시, 형판 목록, 노브 값, 배 시드.
- 지금 코드는 해시 집합을 그냥 순회하는 곳이 있음(방 계산). 해시 집합 순회 순서는 보장되지 않으므로 구조층 계산은 **항상 좌표를 정렬한 순서로** 처리하고, 결과도 정렬해서 내놓음.
- 무작위가 필요한 곳(형판 변형, greeble 선택)은 전역 난수를 쓰지 않고 "배 시드 + 칸 좌표"를 섞은 해시로 값을 만듦. 그러면 이웃 칸이 바뀌어도 그 칸의 값은 안 바뀜.
- 검증: 같은 입력을 두 번 돌린 결과가 같은지, 입력 칸 순서를 섞어도 같은지를 자동 테스트로 확인함(9절).

## 4. 외피 생성기

### 4.1 문제

생성기는 지금 "방 목록"을 읽음. 구조층이 들어오면 외피는 방이 아니라 "거주 칸 + 구조 칸" 전체를 감싸야 하고, 창은 방이 아니라 칸의 면 단위로 정해져야 함. 설계 문서 0.3절과 13.4절 3번은 이미 "생성기 입력을 선체 칸 집합으로 바꾼다"를 다음 할 일로 적어 둠.

### 4.2 후보

1. 방 목록 입력을 유지하고 구조 칸만 덧붙여 읽기.
2. 입력을 "선체 칸 집합(칸마다 거주/구조 표시) + 창 면 목록 + 형판에서 나온 큰 부품 자리"로 교체(13.4절 3번을 이번에 같이 함).

### 4.3 선택과 이유

**2번을 추천함.** 구조층을 넣는 순간 생성기는 어차피 방이 아닌 칸을 다뤄야 하므로 13.4절 3번을 따로 할 이유가 없어짐. **그래서 13.4절 3번을 이 계획의 1단계에 흡수하고, 순서도 13.4절 1번(문 상태)과 2번(진공 구역)보다 앞당기기를 제안함.** 특히 2번 진공 구역은 "외피 구멍 → 그 방이 진공"을 전제로 하는데, 구조층이 생기면 외피 구멍과 방 사이에 구조 칸이 끼므로 진공 규칙의 모양이 바뀜. 진공을 먼저 만들면 다시 고쳐야 함. 순서 변경은 사용자가 정할 일이라 열린 질문에도 올림(10절 5번).

다만 지금 씬의 방 목록 데이터를 버리지는 않음. 1단계에서는 **기존 방 목록에서 거주 칸 집합과 창 면을 뽑아내는 변환**을 앞에 붙여서, 데이터 이전 없이 새 입력 방식을 쓸 수 있게 함.

### 4.4 바뀌는 입력과 출력

| | 지금 | 구조층 후 |
|---|---|---|
| 입력 | 방 목록, 막힌 칸(엔진 자리), 절대 좌표 추가 부품 | 거주 칸 집합, 구조 칸 사전, 창 면 목록, 형판이 내놓은 큰 부품 자리 |
| 지붕, 밑판 | 방 칸마다 | 선체 칸 전부(거주 + 구조) |
| 바깥 벽 | 방 칸의 빈 이웃 변 | 선체 칸 집합의 빈 이웃 변. 창 면이면 창 벽 |
| 모서리 | 볼록만 | 볼록 + **오목**. 구조층 윤곽은 오목한 꺾임이 반드시 생기므로 오목 모서리 조각이 1단계부터 필요함 |
| 방 지붕 덮개 | 방마다 | 방이 외피 안쪽에 묻히므로 의미가 바뀜. 1단계에서는 끄고, 2단계에서 형판(엔진 포드 덮개, 탱크 돔 등) 쪽 부품으로 다시 묶음 |
| 뱃머리, 용골, 함교 차양, 엔진 | 절대 좌표 | 형판이 계산한 자리에 놓음. 1단계에서는 꺼 두고 2단계에서 옮김 |
| 거주/구조 경계 | 없음 | 외피가 만들지 않음. 거주 칸 쪽 안쪽 벽(지금의 `InnerWalls_NearFull`)이 그대로 경계 역할을 함 |

### 4.5 여기서 터질 것

- 형판을 쓰기 전에는 띠가 균일해서 "두꺼워진 호텔"이 될 수 있음. 1단계 판정에서 그렇게 보이면 정상이고, 2단계 형판이 해결할 몫임.
- 오목 모서리가 없으면 꺾인 곳에 구멍이 뚫려 보임.
- 창이 필요한 방을 표시하지 않으면 함교와 창가 방의 창이 전부 사라짐.

## 5. 내부 뷰 표현

### 5.1 문제

뚜껑을 열면 지금은 외피 전체를 "그림자만" 모드로 숨김. 구조층은 숨기면 안 되고 "어둡게, 기계로 꽉 찬 단면"으로 보여야 함. 그런데 카메라가 70m 뒤에서 40도 아래로 내려다보는 망원이라, 높이가 있는 물체는 그 뒤쪽 바닥을 대략 자기 높이만큼(조금 더) 가림. 구조층을 방 높이 그대로 세워 두면 카메라 쪽 구조층이 앞줄 방을 덮음.

### 5.2 후보

1. **구조층을 바닥 높이의 납작한 어두운 판으로만 보이기.** FTL처럼 위에서 본 평면도 느낌. 싸고 절대 안 가리지만 부피감이 없음.
2. **방 사이 벽과 같은 규칙으로 높이를 나누기.** 카메라 쪽 구조층은 낮은 높이에서 자르고, 반대쪽 구조층은 방 높이 가까이 세워 둠. 반대쪽은 원래 바깥 벽이 온전한 높이로 서 있는 쪽이라 가리는 문제가 없고, 오히려 "벽 뒤에 기계가 쌓인" 부피감이 생김.
3. **셰이더로 자르는 면 하나를 두고 모든 구조층 표면을 그 위로 버리기.** 잘린 면은 어둡게 칠함(뒷면을 단색으로 그리는 흔한 단면 기법). 높이 하나로 모든 소품까지 한 번에 잘려서 greeble이 많아져도 규칙이 하나로 유지됨.

### 5.3 선택과 이유

**1단계는 1번, 3단계(내부 뷰 단계)에서 2번 규칙을 3번 기법으로 구현하는 것을 추천함.**
- 1번은 첫 판정 화면을 가장 싸게 만듦. "방 바깥이 어두운 기계 덩어리"라는 인상이 맞는지부터 봐야 함.
- 2번 규칙은 이미 검증된 벽 낮추기 규칙(카메라 반대쪽 바깥 벽만 온전한 높이)과 같은 논리라 플레이어가 새로 익힐 것이 없음. 카메라가 항상 대각선이라 어느 변이 카메라 쪽인지가 늘 분명함.
- 3번 기법은 설계 문서 1장의 "셰이더 하나가 벽 자르기를 맡는다"와 같은 방향임. 소품마다 낮은 복제본을 만드는 지금 벽 방식은 greeble 수가 늘면 감당이 안 됨.
- 블록아웃 단계(셰이더가 아직 없음)에서는 구조 칸 상자의 높이를 바꿔 끼우는 방식으로 2번 규칙만 먼저 확인할 수 있음.

### 5.4 구현 방식 (코드 없이, 순서대로)

1. 구조층 렌더러는 `Exterior`와 **다른 그룹**에 둠. 그래야 뚜껑 열기가 외피를 "그림자만"으로 바꿀 때 구조층이 같이 사라지지 않음.
2. 뚜껑을 닫으면 구조층 렌더러를 전부 끔(외피가 덮으므로 보일 일이 없고, 그리는 비용과 그림자 비용을 아낌).
3. 뚜껑을 열면 구조층을 켜고, 칸마다 "카메라 쪽인가"를 정함. 기준은 그 구조 칸에서 가장 가까운 거주 칸 쪽을 향한 방향과 카메라 방향의 관계로, 지금 바깥 벽 낮추기와 같은 판정임. 카메라 쪽 칸은 낮은 자름 높이, 반대쪽 칸은 높은 자름 높이를 받음.
4. Q/E로 화면을 돌리면 3번을 다시 계산함(지금 벽 다시 정하기와 같은 시점).
5. 잘린 면은 어두운 단색에 약한 무늬(사선 해칭이나 격자)를 줘서 "단면"으로 읽히게 함. 방 바닥보다 확실히 어둡게.
6. 방 조명이 구조층을 비추지 않게 구조층을 별도 렌더링 레이어로 둠(8장 "방별 렌더링 레이어"와 같은 장치). 구조층은 약한 환경광과 자체 발광 몇 점(경고등, 계기)으로만 보이게 함.
7. 구조층은 내부 뷰에서 그림자를 드리우지 않음. 외피가 이미 "그림자만" 모드로 별빛을 막고 있어서 구조층 그림자는 중복이고 비용만 듦. 그림자를 받는 것은 단계 3에서 화면을 보고 정함.

### 5.5 방 사이 벽 낮추기와의 관계

- 방 사이 벽은 지금처럼 전부 낮춤. 구조층과 무관함.
- 거주 칸과 구조 칸 사이의 경계 벽(지금의 바깥 벽 안쪽 면)은 지금 규칙 그대로 카메라 쪽만 낮춤. 구조층의 높이 나누기가 이 규칙과 같은 방향이라 "낮은 벽 뒤에 낮은 기계, 높은 벽 뒤에 높은 기계"로 일관됨.
- 변 편집기는 거주 칸 사이 변만 다루므로 영향 없음. 단, 구조 칸이 `Floors` 그룹에 들어가면 변 편집기가 걸을 수 있는 칸으로 읽어 버리므로 **구조층은 절대 `Floors` 아래에 두지 않음**.

### 5.6 그림자 거리 110m 문제

- 외피가 구조층 두께만큼 바깥으로 커지므로 그림자가 덮어야 할 범위가 넓어짐. 대략 배 한 변이 기본 띠 두께의 두 배만큼, 형판 돌출만큼 더 길어짐.
- 지금 110m는 카메라가 70m 뒤에 있어서 늘린 값이고, 배가 커지면 그림자 지도 한 장이 덮는 범위가 넓어져 그림자가 흐려질 수 있음.
- 대응 순서: 먼저 구조층 그림자를 끔(5.4절 7번). 그다음 단계 3에서 화면으로 그림자 품질을 보고, 부족하면 그림자 단계 분할(cascade) 비율과 그림자 거리를 조정함. 그래도 부족하면 설계 문서 4.1절의 대안(직교 카메라)을 다시 검토함.

### 5.7 여기서 터질 것

- 구조층을 두껍게(4칸) 잡으면 카메라 쪽 낮은 자름 높이도 플레이어가 그 근처 방 가장자리에 섰을 때 캡슐을 일부 가릴 수 있음. 단계 3의 확인 항목에 "네 방향 회전 모두에서 가장자리 방 안의 캡슐이 보이는가"를 넣음.
- 잘린 면이 방 바닥과 같은 높이 근처면 바닥과 섞여 경계가 흐려짐. 자름 높이를 바닥보다 확실히 높게 두거나 색 대비로 구분함.

### 5.8 조절 가능한 것

- 카메라 쪽 자름 높이: 낮을수록 안 가리지만 납작해짐.
- 반대쪽 자름 높이: 높을수록 부피감이 커지지만 배 끝자락의 방을 볼 때 답답해짐.
- 단면 색의 밝기와 무늬 세기: 어두울수록 방이 도드라지고, 밝을수록 기계가 읽힘.

## 6. 드론 수리 대상화

### 6.1 문제

구조 칸이 드론 수리 대상이 되기로 함. 그런데 드론 시스템, 길찾기, 작업 대기열, 손상 원인(공허부식)이 아직 하나도 없음. 지금 만들 것과 나중에 붙일 것을 갈라야 함.

### 6.2 지금 만들 최소한

- **내구도 값**: 구조 칸마다 하나. 저장 대상(3.5절).
- **수리 지점 자리**: ~~취소됨(0.1절 3번).~~ 구조 칸은 개별 수리 지점을 갖지 않음. 수리는 선체 전체가 보강되는 추상 표현으로 하며, 어떤 값을 올리는 방식인지는 단계 4 전에 6절을 고쳐 쓰면서 정함.
- **확인용 디버그 조작**: 키 하나로 시드 기반 무작위 구조 칸 몇 개를 손상시키고, 다른 키로 전부 고침. 손상된 칸은 내부 뷰 단면 색을 붉게 섞어 표시함. 실제 손상 원인과 수리 행동은 아님.
- **이어받기 확인**: 손상시킨 뒤 거주 칸을 바꿔 재계산했을 때 남은 칸의 손상이 유지되는지.

### 6.3 나중에 붙일 것 (이번 범위 밖, 자리만 남김)

- 드론 작업 대기열과 우선순위 지시(외피 수리처럼 플레이어가 우선순위를 지시).
- ~~드론이 구조 칸까지 가는 경로.~~ 취소됨(0.1절 3번). 구조층은 드론이 방문하지 않음.
- 손상 전파: 외피 손상 → 구조 칸 손상 → 구조 칸이 무너지면 맞닿은 거주 칸 쪽 경계에 구멍 → 그 방이 진공. 진공 구역 설계(13.4절 2번)와 묶어서 정함.
- 배관 망, 전력 망: 3.4절의 망 번호 자리를 채우고, 구조 칸 손상이 그 망에 속한 모듈의 기능을 떨어뜨리는 규칙.
- 수리 자원 소비, 시대별 구조 칸 외형 차이.

## 7. 소품(greeble) 채움

### 7.1 문제

내부 뷰 단면이 상자만으로 채워지면 "어두운 벽"이지 "기계로 꽉 찬 구역"으로 안 읽힘. 칸마다 소품을 채워야 하는데, 손으로 배치하면 배가 바뀔 때마다 다시 해야 하고, 무작위로 하면 세이브를 불러올 때마다 달라짐.

### 7.2 배치 방식

- **소품 풀 데이터**: 소품마다 프리팹, 차지 칸 크기(1×1, 1×2, 2×2 정도의 몇 가지 규격), 높이 등급(낮음, 중간, 높음), 어울리는 역할(일반, 엔진, 탱크, 배관), 가중치, 방향 조건(거주 칸 쪽을 향해야 하는 패널 등)을 적음.
- **칸 묶음 단위로 고르기**: 구조 칸을 2×2칸 고정 격자로 묶고, 묶음마다 "배 시드 + 묶음 좌표" 해시로 큰 소품부터 놓아 보고 남는 칸을 작은 소품으로 채움. 묶음 경계가 고정이라 거주 칸이 바뀌어도 바뀐 근처 묶음만 다시 정해지고 나머지는 그대로임. 칸 하나하나 따로 고르면 2×2 소품을 못 쓰고, 배 전체를 한 번에 채워 넣으면 칸 하나만 바뀌어도 전체가 뒤섞임.
- **역할 우선**: 엔진 자리 칸에는 엔진 계통 소품, 탱크 형판 칸에는 탱크만 오게 해서 단면이 구역별로 다르게 읽히게 함.
- **자름 높이와 맞추기**: 내부 뷰에서는 위에서 잘린 모습이 주로 보이므로, 소품은 위에서 본 단면(둥근 탱크 윗면, 이어진 파이프)이 읽히게 고름. 높이 등급은 5절의 카메라 쪽/반대쪽 자름 높이와 짝을 맞춤.
- **저장하지 않음**: 소품은 칸 데이터와 시드에서 다시 만들어지므로 세이브에 안 들어감.

### 7.3 에셋 출처 후보와 평가 기준

선체 구조(벽, 모서리, 지붕, 시대 키트)는 자체 키트 유지. 외부 에셋과 AI 생성 모델은 **greeble 소품에만** 쓰고, 재질은 전부 자체 셰이더로 덮어서 통일함.

| 후보 | 장점 | 확인할 것 |
|---|---|---|
| CC0 저폴리 키트(예: Kenney, Quaternius의 공상과학 키트) | 라이선스 부담이 거의 없음, 폴리 수 낮음 | 깎은 중간 폴리곤 그림체와 맞는가, 너무 장난감 같지 않은가 |
| Unity Asset Store 하드서피스/공업 소품 팩 | 양이 많고 품질 고름 | 표준 EULA의 게임 포함 조건, 팩마다 붙은 추가 조건 |
| Sketchfab 등의 CC0, CC-BY 모델 | 개별 고품질 소품 | CC-BY는 출처 표기 의무. 비상업(NC), 변경 금지(ND)는 제외 |
| AI 생성 모델(이 환경의 Unity MCP 모델 생성 기능 포함) | 원하는 모양을 바로 얻음 | 생성 서비스 약관의 상업 이용과 소유권, 토폴로지 품질, 폴리 수 |

평가 기준(소품마다 체크):
1. **라이선스**: 상업 게임 포함 가능, 변경 가능, 재배포 조건. 출처 표기 의무가 있으면 기록. 확인되지 않은 것은 쓰지 않음.
2. **폴리 수**: 소품 하나당 예산을 정하고(출발값은 수백~이천 삼각형 안팎), 칸당 합계 예산도 정함. 예산을 넘으면 Blender에서 줄이거나 탈락.
3. **재질을 덮어도 형태가 읽히는가**: 원래 텍스처와 노멀 맵을 버리고 자체 셰이더 단색+무늬로 덮었을 때도 모양이 읽혀야 함. 형태가 텍스처에 기대는 에셋은 탈락. 깎인 모서리가 실제 형상으로 있는 것을 우선함.
4. **위에서 잘린 단면이 읽히는가**: 내부 뷰에서 주로 보이는 모습.
5. **규격 맞추기**: 1m 칸 규격, 피벗(바닥 가운데), 방향을 맞출 수 있는가.
6. **그림체 일치**: 깎은 중간 폴리곤과 어울리는가.

재질 덮기: 외부 모델은 UV가 자체 트림 시트와 맞지 않으므로, 자체 셰이더는 UV 대신 위치 기반 무늬(세 방향 투영)와 꼭짓점 색 또는 소품 번호로 색을 고르는 방식을 씀. 셰이더(설계 문서 5장의 ShipSurface)가 아직 없으므로 그 전까지는 어두운 단색 재질 하나로 덮음.

기록: 들여온 에셋마다 출처 주소, 저작자, 라이선스, 받은 날, 고친 내용을 `Docs/ThirdPartyAssets.md`(신규)에 적음. 기록 없는 외부 에셋은 저장소에 넣지 않음.

## 8. 단계 분할

각 단계는 독립적으로 멈출 수 있음. 단계마다 **사용자가 판정할 화면**을 적음. 판정 결과(예: "두껍다", "밍밍하다")를 듣고 노브를 돌린 뒤 다음 단계로 넘어감.

작업은 **`ShipBlockout_Large.unity`를 복제한 새 씬**(가칭 `ShipBlockout_Structure.unity`)에서 하는 것을 추천함. 기존 씬은 비교 기준으로 그대로 둠(열린 질문 10절 6번).

### 단계 1: 구조 칸 두께만 채우고 윤곽 비교 (가장 작게)

- 기존 방 목록에서 거주 칸 집합과 창 면을 뽑는 변환을 앞에 붙임.
- 자동 채움 1~3번(기본 띠, 움푹한 곳 메우기, 창 면 예외)과 7번(거주 칸 우선)만 구현. 형판과 대칭은 아직 없음.
- 구조 칸마다 어두운 회색 블록아웃 상자를 놓음(구조층 그룹, `Floors`와 `Exterior` 밖).
- 생성기가 거주 칸 + 구조 칸을 감싸도록 입력을 바꿈. 오목 모서리 조각을 블록아웃 수준으로 새로 만듦. 방 지붕 덮개와 절대 좌표 추가 부품, 손으로 놓은 부착물은 끔.
- "구조층 끔"으로 돌리면 지금과 같은 외피가 나오게 둠(비교용).
- 내부 뷰: 구조층을 바닥 높이의 납작한 어두운 판으로만 보임(5.2절 1번).
- **판정 화면**: 외부 궤도 뷰에서 구조층 켬/끔 전후 스크린샷(같은 각도 두 장씩, 뒤쪽과 앞쪽). 내부 뷰에서 방 바깥이 어두운 판으로 채워진 전체 화면 한 장.
- **수용 기준**:
  - 두께 노브를 바꾸고 다시 생성하면 윤곽이 그에 맞게 바뀜.
  - 같은 입력으로 두 번 생성한 구조 칸 목록이 같음(개수와 정렬된 좌표 목록 비교값을 콘솔에 찍어 확인).
  - 구조층을 끄면 기존 외피 조각 수(676조각 기준, 덮개와 부품 포함)와 같은 구성이 나옴.
  - 변 편집기가 여전히 벽 69, 문 11, 방 10을 읽음. 구조 칸에 벽을 놓으려 하면 빨강(놓을 수 없음)으로 나옴.
  - 함교와 창가 방의 창이 외부에서 보임.
  - Play 후 콘솔에 오류와 경고 없음.

### 단계 2: 윤곽 형판과 큰 부품 자리

- 자동 채움 4~5번(형판 찍기, 대칭) 구현. 첫 형판은 엔진 포드(뒤쪽 돌출, 엔진 자리 역할), 탱크 돌출(옆구리), 용골(아래쪽 가장자리 띠), 등줄기 정도로 시작.
- 엔진, 뱃머리, 용골, 함교 차양을 형판이 계산한 자리에 놓음. 방 지붕 덮개를 형판 부품(엔진 포드 덮개, 탱크 돔)으로 다시 묶음. 기존 막힌 칸(엔진 자리 2×2 세 개)은 엔진 포드 형판의 엔진 자리 역할 칸으로 옮겨 감.
- **판정 화면**: 외부 궤도 뷰 네 방향 스크린샷과, 사용자가 보여 준 FTL 단면 그림을 옆에 놓은 비교. 형판을 하나씩 끄고 켠 화면.
- **수용 기준**: 형판 하나를 끄면 그 돌출만 사라짐. 대칭을 켜면 좌우 윤곽이 같음. 엔진 세 개가 엔진 포드 안에 놓이고 외피를 뚫고 나오거나 떠 있지 않음. 단계 1의 결정론 확인이 그대로 통과함.

### 단계 3: 내부 뷰 단면 표현

- 구조층 높이 나누기(카메라 쪽 낮게, 반대쪽 높게), Q/E 회전 시 재계산, 어두운 단면 재질, 구조층 렌더링 레이어 분리, 구조층 그림자 끔, 뚜껑 닫으면 구조층 끔.
- 블록아웃에서는 상자 높이를 바꿔 끼우는 방식으로 하고, 셰이더 자르기는 ShipSurface 셰이더 작업 때 옮김(열린 질문 10절 7번).
- **판정 화면**: 내부 뷰 네 방향(Q/E) 스크린샷 각각, 그리고 배 가장자리 방에 캐릭터를 세운 확대 화면.
- **수용 기준**: 네 방향 모두에서 가장자리 방 안의 캐릭터 캡슐이 가려지지 않음. 방 바닥과 단면이 색으로 확실히 구분됨. 뚜껑을 닫으면 구조층이 안 그려짐(프레임 디버거나 렌더러 수로 확인). 그림자 거리 110m에서 그림자 품질이 단계 1 대비 눈에 띄게 나빠졌는지 판정(나빠졌으면 5.6절 대응).

### 단계 4: 구조 칸 데이터, 내구도, 저장 기록

- 구조 칸 상태(역할, 출처, 내구도, 망 번호 자리, 시대 자리) 정리. 저장 기록 형태를 정하고 "저장 → 불러오기 → 같은가" 왕복만 만듦(세이브 시스템 자체는 아직 없으므로 왕복 확인까지만).
- 디버그 손상/수리 키, 손상 칸의 단면 붉은 표시, 수리 지점 위치 계산과 기즈모 표시.
- 거주 칸 변화 재계산 시 이어받기(자동 채움 6번). 거주 칸을 바꾸는 도구가 아직 없으므로, 에디터 메뉴로 "방 하나를 한 칸 넓혀 재계산" 같은 확인용 조작을 둠.
- 이 단계 전에 테스트용 어셈블리 정의 파일을 만들어 계산 부분을 자동 테스트할 수 있게 함(지금 저장소에 asmdef와 테스트가 없음).
- **판정 화면**: 손상 키를 누른 뒤 내부 뷰에서 붉게 표시된 구조 칸, 수리 지점 기즈모가 외피 바깥에 붙은 씬 뷰.
- **수용 기준**: 자동 테스트로 확인 — 같은 입력 같은 결과, 입력 순서를 섞어도 같은 결과, 저장 왕복 동일, 재계산 후 살아남은 칸의 손상 유지, 새 칸은 내구도 가득, 거주 칸이 이긴 칸은 구조 칸에서 빠짐.

### 단계 5: greeble 채움

- 먼저 기본 도형(원통, 상자, 반구)으로 만든 임시 소품 열 개 안팎으로 풀과 배치 규칙(7.2절)을 완성함.
- 그다음 7.3절 기준으로 외부/AI 소품을 고르고, 라이선스 기록을 남긴 뒤 임시 소품을 교체함.
- **판정 화면**: 내부 뷰 전체와 확대(엔진 포드 구역, 탱크 구역, 일반 구역 각각). 시드만 바꾼 두 장 비교.
- **수용 기준**: 같은 시드면 같은 배치, 거주 칸 한 칸 변경 시 바뀐 근처 묶음 밖의 소품은 그대로. 렌더 비용을 측정해 기록(배치 호출 수, 그려지는 삼각형 수, 프레임 시간, 구조층 켬/끔 비교). 들인 모든 외부 에셋이 `Docs/ThirdPartyAssets.md`에 기록돼 있음.

### 단계 뒤처리

- 단계 1~3이 판정을 통과하면 `Docs/ShipBuildDesign.md`에 0.5절(구조층)을 추가하고 13장의 할 일 순서를 고침.
- 단계마다 별도 리뷰 에이전트로 코드 리뷰를 돌리고 결과를 심각도와 함께 보고함.

### 10.2 사용자가 정해야 할 열린 질문

1. **구조 칸 목록을 세이브에 통째로 저장할까, 손상만 저장하고 모양은 불러올 때 다시 계산할까?** 추천은 통째로 저장(규칙을 고쳐도 옛 세이브 모양이 안 바뀜). 대신 세이브가 조금 커지고, "세이브에는 칸 목록과 모듈 배치만" 원칙에서 칸 목록의 범위가 구조 칸까지 넓어짐.
2. **거주 칸이 넓어져 구조 칸이 사라질 때 그 칸의 손상은 버려도 되나?** 추천은 버림(확장 공사가 낡은 구조를 걷어 낸 것으로 봄). 손상을 이웃 구조 칸으로 넘기는 방법도 있음.
3. **외피와 맞닿지 않은 안쪽 구조 칸을 드론이 어떻게 고치나?** 바깥 외피 쪽에서 파고드는 것으로 볼지, 안쪽 점검 통로(걷지 못하는 드론 전용 통로)를 둘지. 드론 길찾기 그래프 모양이 달라짐.
4. **엔진은 거주 층의 모듈인가, 구조층의 부품인가?** 0.1절은 "엔진은 격자 칸을 차지하는 모듈"이라 했고, 지금 코드는 엔진 자리를 "방이 아닌 막힌 칸"으로 둠. 추천은 엔진 자리를 구조 칸(엔진 자리 역할)으로 두고 엔진 모듈을 그 위에 놓는 것. 이 경우 거주 칸 확장이 엔진 자리를 밀어낼 수 있는지도 정해야 함.
5. **13.4절 순서를 바꿔도 되나?** 추천은 "생성기 입력 교체(13.4절 3번) + 이 계획 단계 1~3"을 문 상태(1번)와 진공 구역(2번)보다 먼저 하는 것.
6. **새 씬에서 작업할까, `ShipBlockout_Large`를 직접 바꿀까?** 추천은 새 씬(비교 기준 보존).
7. **단면 자르기를 블록아웃용 상자 높이 바꿔 끼우기로 먼저 할까, 이번에 ShipSurface 셰이더 작업을 앞당겨 셰이더로 자를까?** 추천은 블록아웃 방식 먼저. 셰이더는 greeble이 늘어나는 단계 5 전에 필요해짐.
8. **구조층의 기본 두께와 형판의 과감함은 어느 쪽에서 시작할까?** 추천은 일부러 과하게(두께 상한 쪽, 엔진 포드 길게) 잡고 사용자가 "과하다"고 하면 줄이는 것.
9. **대칭을 기본으로 켤까?** 추천은 켬. FTL 레퍼런스 대부분이 대칭이고 윤곽이 배처럼 읽히는 데 가장 싸게 기여함.
10. **여러 층(위아래 층)으로 갈 때 구조층이 위아래로도 채워지나?** 지금은 한 층이라 평면 띠만 계획함. 여러 층이 되면 층 사이와 맨 위아래에도 구조층(등줄기, 배 밑 장갑)을 둘지 정해야 함.
11. **greeble 외부 에셋에 쓸 예산(유료 팩 허용 여부)과 AI 생성 서비스 허용 여부.** 라이선스 확인 기준은 7.3절.
