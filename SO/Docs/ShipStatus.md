# 우주선 작업 인수 문서

작성 2026-11-24. 우주선(선체, 통로, 모듈) 작업을 다른 세션이 이어받을 때 **가장 먼저 읽는 문서**임. 이 문서는 "지금 어디까지 왔고 무엇이 정해졌고 다음에 무엇을 하는가"만 적음. 자세한 규칙과 이유는 계획서에 있고 여기서는 가리키기만 함.

전체 프로젝트 인수 문서는 [Handoff.md](Handoff.md)임. 이 문서는 그 우주선 절의 상세판임.

---

## 1. 한 줄 상태

통로 그물 + 세그먼트/모듈 분리 모델의 **계획서가 3차 개정까지 끝났고(구현 전. 사용자 승인은 받았고 critic 비평도 반영함)**, 구현은 A0(통로 그물 판만 깔기)까지 끝남. **다음은 A1(세그먼트 판) 구현이고, 사용자 승인을 받음**(2026-11-25. 순서: 계획서 critic 비평 → A0 커밋 → SampleScene 정리 커밋 → A1). A0 결과물은 커밋함(8절).

## 2. 결정된 것 (사용자 확정, 2026-11-24)

충돌하면 `ShipBuildDesign.md` 0.x절과 `ShipLayoutNetworkPlan.md`가 옛 본문보다 우선함.

| 항목 | 결정 |
|---|---|
| 칸과 높이 | 칸 1m, 방 안 높이 3m, 층 높이 4m. PC 전용, 그림체는 깎은 중간 폴리곤 |
| 통로 폭 | **간선 2칸, 지선 1칸.** `ShipBuildDesign.md` 0.1절의 "복도 1칸"을 사용자가 의식적으로 바꿈. 간선 폭은 걸어 보고 조정할 노브 |
| 작은 방 | 2×2, 2×3 허용(에어락, 창고 같은 작은 모듈). 기능 방은 3×3~4×4 유지 |
| 용어 | **세그먼트**(선체 덩어리, 백팩 배틀즈의 가방) / **가압구역**(걷는 영역: 통로 칸 + 방칸) / **설비구역**(못 걷는 내부 영역, 배관·기계·탱크) |
| 구조 | 세그먼트가 먼저 있고 모듈은 그 위의 **별개 목록**. 초기 우주선 = 세그먼트 배치 + 모듈 배치의 프리셋 |
| 모듈 놓는 칸 | **가압구역의 빈 방칸에만.** 엔진, 탱크는 모듈이 아니라 설비구역에 고정된 세그먼트 부품 |
| 경계 걸침 | **모듈은 세그먼트 경계를 걸칠 수 있음.** 걸친 모듈이 있는 접합부는 모듈을 먼저 치워야 분리 가능(계획서 7.4절) |
| 모듈은 걸음을 막음 | **모듈이 차지한 N×M 칸 전체가 걸음을 막음**(충돌체가 점유 칸 전체를 덮음). 막힌 곳은 돌아가는 것이 정상이고, **동면 전에 배치를 잘 생각하는 것이 플레이의 일부**임. 배치가 방 사이 이동 시간을 바꾸고 그것이 사건에 대응하는 시간에 영향을 줌(본부의 이벤트 엔진과 프로토타입이 이동 시간을 씀). A2의 사용자 판정은 "막혀도 되는가"가 아니라 "막힌 모양이 걸을 만한가"(취향). 계획서 12.2절 |
| 완전히 끊기는 배치는 놓을 때 막음 | 배치, 편집, 개조 시점에 "여기엔 못 놓음"으로 거부함(놓기 규칙 6: 배의 모든 빈 방칸과 모든 모듈의 접근 칸이 통로 그물에서 닿아야 함). 차단막 닫힘, 불, 진공, 파손 같은 게임 중 상태 변화로 생기는 일시 단절은 허용. 이유: 본부 이벤트 엔진이 모듈 이름으로 장소를 조회해 걸어가므로 "못 가는 장소" 분기를 안 가져도 되게 함. 계획서 12.2절 |
| 차단막 | 통로 중간과 접합부에 차단막(도어락)을 둠. 접합부는 분리 지점. 접합 통로 변은 차단막 고정 |
| 설비구역 | 드론이 방문하지 않음. 내구도 값만 가짐. 수리는 선체 전체 보강이라는 추상 표현 |
| 확장 | 세그먼트 붙이기 + '개조 가능' 표시가 붙은 설비 칸만 개조. 핵심 구조(엔진 자리, 장갑)는 개조 불가 |
| 배치 | 월드가 아니라 **배치 패널**에서 함(백팩 배틀즈, JumpSpace, FTL 전개도 참고). 패널은 아직 안 만듦 |
| 에셋 | 보유 에셋만 사용(AI 생성, 유료 팩 불가). `Assets/Imports` 원본은 수정 금지, 쓸 것만 복사하고 복사본 머티리얼만 URP Lit으로 고침 |
| 형식 1 | 구조층 1차 구현(아래 5.2)은 "동작과 출력 불변"으로 동결. 새 모델은 별도 경로로 만듦 |

**사용자가 정하지 않은 것**: 계획서의 열린 질문은 **없음**. 옛 4번(모듈이 걸음을 막는가)과 6번(완전히 끊기는 배치)은 사용자가 결정함(위 표). 나머지(분리된 모듈은 보관함으로, 분리된 세그먼트는 버림, 접합 방칸↔방칸은 열린 변, 세그먼트 회전은 D 뒤)는 AI가 추천대로 정해서 12.2절 "결정됨"에 있음.

## 4. 모델 요약 (계획서를 안 읽는 사람용)

- **세그먼트** 하나는 자기 윤곽, 가압구역(통로 칸과 방칸), 설비구역, 접합부를 한 덩어리로 가짐. 문자 격자(텍스트 파일)로 정의함.
- **모듈**(조종석, 치료 베이, 재배 베이 등)은 세그먼트와 별개로 저장되고, 이어진 세그먼트 전체의 방칸 합집합 위에 놓임. 회전 가능.
- **프리셋**이 초기 우주선임: "어느 세그먼트를 어디에 붙였고, 어느 모듈을 어디에 놓았는가"의 목록.
- **방은 저장하지 않고 계산함**(벽과 닫힌 문으로 막힌 칸 덩어리). 방 이름은 놓인 모듈이 정함.
- **접합부**는 두 세그먼트가 맞닿는 곳이고 분리 지점임. 변 상태(없음, 벽, 문, 차단막)는 변마다 주인이 하나이며 접합 변은 접합부가 가짐.
- 데이터는 "배치 데이터 한 덩어리 → 생성기 → 3D" 구조여야 함. 씬에 손으로 놓은 방과 벽에 의존하면 패널이 못 붙음.

## 7. 알려진 문제 (처리 시점이 정해진 것)

**A0 코드 리뷰(COMMENT, Critical/High 없음)에서 나와 B1a로 미룬 것**
- 막다른 길 근사가 고리 모양 막다른 가지를 못 잡음(4×5 영역 전수에서 216개가 빠져나감, 전부 구멍 있는 고리).
- 폭 3 검사가 3×3 묶음만 봄. 오류 메시지의 줄 번호가 주석을 뺀 번호라 파일 줄과 어긋남. 문 앞 칸을 Validate가 채우고 Build가 그 값에 기댐. `StructureHeight`가 0 이하일 때 0으로 나눔. 좌표계가 섞임(지금은 전부 원점이라 문제없음).

**구조층 1차 구현(형식 1) 리뷰에서 나온 것 — 동결이라 안 고침**
- 형판 폭이 홀짝에 따라 1칸 좁아짐, 단면 위에 소품이 뜨는 경우, 좌표계 혼재, 재생성 시 재질 누수, 결정론 자동 테스트 없음. 허공에 찍던 분기는 가드 위반이지만 동결 원칙에 따라 B1a 이후 처리.

**계획서가 걱정으로 적은 것**
- B1a는 화면 판정이 없어서 "화면이 A2와 같음 + 테스트 통과"가 판정을 대신함.
- 문 둘인 구획 경고가 "콘솔 경고 0" 기준과 부딪칠 수 있음. 첫 형판에 그런 구획을 안 두는 것으로 피함.
- 진공 구획 계산에는 `ShipEdgeGrid`를 재사용할 수 없음(열린 일반 문도 경계로 봄). 나중에 새로 만들어야 함.

## 9. 작업 규칙 (이 작업에서 지킨 것)

- **에러를 가드로 덮지 않는다.** 원인을 모르면 추측으로 패치하지 말고 "모름"으로 보고. 방어 코드는 신뢰 경계(문자 격자 파싱 등)에서 `throw`/`LogError`로 드러내는 것만 허용하고 이유 주석을 단다.
- **작성과 리뷰를 분리한다.** 새 코드는 별도 컨텍스트의 `code-reviewer`가 본다. 계획서는 `critic`이 본다(이번 계획서는 critic 2차 비평 뒤 3차 개정까지 했고, 3차 개정본은 2026-11-25에 새 컨텍스트 critic이 한 번 비평했고 10개를 반영함(계획서 17절)).
- **증거 없이 완료라고 하지 않는다.** Play 실행, 콘솔 확인, 스크린샷으로 확인하고, 안 한 건 "안 했음"이라고 적는다.
- **사용자는 취향 판정만 한다.** 구조 결정은 AI가 추천과 함께 정하고, 재미와 예쁨은 화면을 보고 사용자가 한 마디로 판정함. 기본값이 밍밍해지는 쪽으로 치우치니 일부러 극단까지 밀고 사용자가 되돌리게 함.
- 코딩 규약: 새 C# 스크립트는 `Assets/Scripts/ShipBlockout/` 아래 `SpaceOdyssey.Blockout`. 코드 인용과 구체적 수치를 구조 노트에 쓰지 않음(값의 의미를 씀).

### Unity 에디터를 같이 쓰는 규칙
- **에디터는 하나이고 여러 세션이 같이 씀.** 씬 열기, Play, 스크립트 수정(재컴파일)은 서로의 Play를 끊을 수 있음. 지금 합의된 순서: 우주선 쪽과 프로토타입 쪽(세션 이름 `본부`)이 **번갈아 쓰고, 쓰기 전에 서로 한 줄로 알림.** 마지막 상태: `ShipBlockout_Network` 열림, Play 꺼짐, 저장 안 한 변경 없음, 에디터는 우주선 쪽이 쓰는 차례.
- **Unity MCP**(`mcp__UnityMCP__*`): 인스턴스가 둘 붙어 있을 수 있음. 이 프로젝트는 `SO@852e7e0c`. `Dew@e610a44f`는 **다른 프로젝트라 건드리지 마라.** 호출마다 `unity_instance`를 주거나 `set_active_instance`로 고정.
- `execute_code`에는 `using`을 쓸 수 없음(형식은 전체 경로로). 스크립트를 만지면 `read_console`로 컴파일 에러를 확인하고 도메인 리로드가 끝난 뒤 다음 작업. Unity 6000.6.10f1, URP 17.6, Cinemachine 3, Input System 전용이라 API 이름은 훈련 기억 대신 `unity_reflect`/`unity_docs`로 확인.
- 이 환경에서는 `Mouse.current`에 큐로 넣은 입력이 실제 마우스 위치에 덮어씌워지고, 에디터가 포커스를 잃으면 Play 프레임이 멈춤. 키보드는 큐로 흉내 낼 수 있음.
