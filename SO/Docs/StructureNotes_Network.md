## 1. 문자 격자 한 장 = 배 한 척

### 문제
"통로가 FTL 같은가"를 보려면 꺾이고 갈라지는 통로를 담은 배가 하나 필요했음. 기존 배치 데이터는 방을 직사각형 목록으로만 받아서 꺾인 통로를 담을 수 없고, 고치면 형식 1 동결 원칙(계획서 5.5절)을 어김.

### 후보
1. 기존 배치 데이터에 통로 칸 목록을 덧붙이기.
2. 새 데이터 에셋(스크립터블 오브젝트)을 1a부터 만들기.
3. 글자 행으로 된 텍스트 파일 한 장(계획서 2.7절의 문자 격자 표기).

### 선택과 이유
3번. 계획서가 이미 형판 표기로 문자 격자를 정했고, 1a는 데이터 모양을 확정하는 단계가 아님. 텍스트 파일이면 평면도가 파일 그대로 보이고, 사용자가 "답답하다" 판정을 내렸을 때 글자 몇 개만 바꾸면 됨. 저장소 변경 내역에서 바뀐 칸이 눈에 보임. 형식 2 데이터 에셋은 1b에서 만듦.

### 구현 방식
1. 파일 `Assets/Prefabs/Ship/Network/Ship01_1a.txt`. 세미콜론으로 시작하는 줄은 주석이고, 머리 주석에 글자 뜻이 적혀 있음.
2. 한 줄이 칸 한 줄. 오른쪽이 뱃머리, 왼쪽이 엔진. 맨 윗줄이 배의 한쪽 옆구리.
3. 글자 묶음은 셋: 기호(우주, 구조 역할 넷, 통로, 시작 위치), 대문자(모듈 자리. 자리마다 다른 글자), 소문자(그 자리의 문 칸).
4. 문 칸은 따로 좌표 목록으로 적지 않고 자리 안의 칸 하나를 소문자로 적음. 그 칸이 맞닿은 통로 칸 쪽 변이 문 변임.

### 여기서 터진 것
- 문 변을 좌표 목록으로 적으면 손으로 쓰다 한 칸씩 밀림. 소문자 표기로 바꿔서 평면도 안에서 바로 보이게 함.
- 윤곽에 탱크 돌기를 더했더니, 우주에 닿아 있던 지선 끝이 선체 안으로 묻혀 앵커 없는 막다른 길이 됨. 지선을 돌기 끝까지 늘여 다시 끝점으로 만듦. 윤곽을 바꾸면 끝점이 사라질 수 있다는 것이 실제로 확인됨(계획서 7.2절 규칙 6과 같은 현상).

### 조절 가능한 것
- 격자 자체: 윤곽 요철, 간선의 꺾임, 지선 길이, 자리 크기. 전부 글자만 바꾸면 됨.
- 간선 폭: 지금은 두 줄로 그림. 넓히려면 한 줄 더 그리면 되지만 검사가 폭 3을 막고 있으므로 검사 규칙도 같이 풀어야 함.

## 2. 첫 배의 모양 (FTL 레퍼런스를 어떻게 옮겼나)

### 문제
AI가 그리는 첫 배는 곧은 복도에 고른 방이 붙은 "격자 사무실"이 되기 쉬움. 사용자 판정 전에 일부러 극단 쪽으로 밀어야 했음.

### 후보
1. 기존 확대판 배의 방 배치를 그대로 두고 통로만 꺾기.
2. 윤곽부터 새로 그리고, 통로를 깎고, 자리를 붙이는 순서(계획서 0.2절).

### 선택과 이유
2번. 1번은 원래 문제(빗살 호텔)의 방 배치를 그대로 끌고 옴.

### 구현 방식 (그린 순서)
1. 윤곽: 가운데 줄 기준 대칭. 엔진 쪽에 포드 셋(위, 가운데, 아래)이 갈라져 튀어나오고, 몸통 위아래로 탱크 돌기와 탱크 둔덕이 붙고, 뱃머리는 두 갈래 송곳니 사이에 짧은 주둥이가 있는 모양.
2. 간선(폭 2): 엔진실에서 나와 몸통 가운데 기계 덩어리를 양쪽으로 감싸는 루프 하나로 갈라졌다가 다시 합쳐지고, 두 번 꺾여 함교로 감. 루프의 위쪽 길과 아래쪽 길은 모양이 다름(아래쪽은 한 번 더 꺾임).
3. 지선(폭 1): 간선에서 갈라져 자리 하나씩으로 감. 둘은 선체 끝까지 가서 끝나는 확장 끝점(위쪽 탱크 돌기, 아래쪽 탱크 둔덕을 관통).
4. 자리: 기능 방 크기(3×3~4×5)와 작은 방(2×2, 2×3)을 섞음. 큰 방(엔진실, 함교, 반응로 등)은 간선 끝이나 옆에, 작은 방은 지선 옆에.
5. 나머지 칸은 전부 구조 구역. 역할은 엔진(엔진 포드 뒤쪽), 탱크(위아래 돌기와 둔덕), 장갑(우주에 닿은 채움 칸), 채움(나머지).
6. 거주 비율은 약 3할로 낮게 잡음. 루프 안쪽의 큰 기계 덩어리 속에 반응로 자리 하나만 짧은 지선으로 파고 들어가 있음.

### 여기서 터진 것
- 아직 판정 전. 위에서 본 화면에서는 배가 로켓처럼 세로로 길쭉하게 읽힘. FTL 배보다 몸통 가운데가 단순할 수 있음.

### 조절 가능한 것
- 거주 비율: 낮을수록 기계 속에 파인 길, 높을수록 호텔. 콘솔에 매번 찍힘.
- 루프 크기: 루프 안 기계 덩어리가 클수록 "돌아가는 길"이 길어짐.
- 자리 크기 편차: 작은 방이 많을수록 평면이 잘게 쪼개져 보임.

## 3. 검사: 격자가 규칙을 어기면 시끄럽게 멈춤

### 문제
손으로 그린 격자는 틀리기 쉬움(줄 길이, 자리 모양, 막다른 길). 조용히 보정하면 사용자가 판정하는 화면이 의도한 배가 아니게 됨.

### 후보
1. 틀린 칸을 건너뛰거나 가까운 종류로 바꾸고 계속 진행.
2. 처음 만나는 위반에서 예외를 던지고 생성을 멈춤.

### 선택과 이유
2번. 격자 파일은 신뢰 경계(사람이 쓴 입력)라서 검증이 맞고, 1번은 가드로 덮기임. 메시지에 파일 이름, 줄과 칸, 자리 글자를 넣음.

### 구현 방식 (검사 순서)
1. 읽기: 줄 길이가 다르면, 알 수 없는 글자가 있으면, 시작 칸이 정확히 하나가 아니면 멈춤.
2. 자리: 같은 글자 칸이 경계 상자를 꽉 채우지 않으면(떨어진 두 덩어리, ㄱ자) 멈춤. 크기가 규격(작은 방 포함) 밖이면 멈춤.
3. 문: 문 칸이 통로 칸과 정확히 한 변만 맞닿아야 함(둘이면 어느 변이 문인지 모호). 문 칸이 없는 자리는 멈춤.
4. 통로 연결: 정렬 순서 첫 통로 칸에서 퍼져서 모든 통로 칸에 닿아야 함. 통로가 이어져 있고 모든 자리에 문이 통로로 나 있으므로 이것으로 모든 자리 도달 가능이 됨.
5. 통로 폭: 3×3이 통째로 통로인 곳이 있으면 멈춤.
6. 막다른 길: 앵커(자리 문 앞 통로 칸, 우주에 닿은 통로 칸)가 아닌데 끝 모양인 칸이 있으면 멈춤. 끝 모양은 둘만 봄: 통로 이웃이 하나 이하인 폭 1 끝, 두 칸이 나란히 앞이 막히고 뒤로만 이어지고 바깥 옆이 막힌 폭 2 끝.

### 여기서 터진 것
- 폭 2 끝을 "이웃이 둘인 칸"으로 잡으면 간선이 꺾이는 바깥 모서리도 끝으로 잡힘. 나란한 두 칸이 같은 쪽으로 막혔고 양옆이 다 막힌 모양만 끝으로 침.
- 이 막다른 길 판정은 1a용 근사임. 최종 방법은 계획서대로 1b에서 테스트와 함께 정함. 지금 방식은 폭 3 이상 통로의 끝을 못 잡지만, 폭 3은 5번 검사가 먼저 막음.
- 일부러 틀린 작은 격자들(알 수 없는 글자, 떨어진 자리, 규격 밖 크기, 문 칸 모호, 문 없음, 끊긴 통로, 폭 3, 폭 1 막다른 길, 폭 2 막다른 길, 시작 칸 둘)로 각각 기대한 메시지가 나오는 것을 확인함. 자동 테스트로 남기지는 않음(1b에서 테스트 어셈블리와 함께).

### 조절 가능한 것
- 자리 크기 규격 목록: 사용자 결정으로 작은 방을 허용함. 규격을 바꾸면 이 목록만 바뀜.
- 앵커의 정의: 지금은 자리 문 앞과 우주에 닿은 칸. 나중에 섹션이 붙으면 "우주에 닿은 칸" 쪽이 바뀜(계획서 3.5절).

## 4. 판 깔기와 막기

### 문제
걸어 보며 간선 폭을 판정해야 하므로 바닥과 못 들어가는 칸이 필요함. 동시에 벽을 세우면 다시 "복도"가 되고 뒤 통로를 가림(계획서 8.4절).

### 후보
1. 거주 칸 둘레에 벽을 세움.
2. 구조 칸을 낮은 판으로만 보이고, 막는 것은 보이지 않는 충돌체로 따로 둠.

### 선택과 이유
2번(계획서 8.4절 1a 행). 보이는 높이와 막는 높이를 떼어 내서, 화면은 평면도처럼 읽히고 걸음은 확실히 막힘.

### 구현 방식
1. 통로 바닥은 밝은 회색 판(간선과 지선 같은 색), 자리 바닥은 자리마다 다른 탁한 색 판. 둘 다 기존 생성기와 같은 이름, 같은 모양과 위치 규칙으로 바닥 그룹에 놓아서 기존 컨트롤러가 손대지 않고 그대로 읽음.
2. 문 칸 앞 통로 바닥에 밝은 줄 하나. 충돌체는 지움(걸음에 걸리면 안 됨).
3. 구조 칸은 바닥보다 조금 높은 어두운 판(역할별 색). 같은 물체의 충돌체만 방 높이까지 늘여서 걸어 들어가지 못함.
4. 외피가 없으므로 우주와 맞닿은 거주 칸(확장 끝점, 뱃머리 쪽 자리)에서 걸어 나갈 수 있음. 그래서 거주 칸에 닿은 우주 칸마다 충돌체만 있는 물체를 둠.
5. 외부 궤도 카메라의 중심을 선체 경계 상자 가운데로 옮기고, 플레이어를 시작 칸으로 옮김. 둘 다 컨트롤러가 깨어나기 전에 해야 해서 미리보기가 먼저 실행됨.
6. 색만 바꾼 재질 복제본은 미리보기가 소유하고 파괴될 때 지움(계획서 8.5절의 누수 지적을 처음부터 피함).
7. 벽, 문 조각, 외피, 단면, 소품, 조명은 만들지 않음. 별빛 하나만 비춤.

### 여기서 터진 것
- 캐릭터 컨트롤러는 물리 쪽 위치를 따로 들고 있어서, 변환만 옮기면 다음 동기화 전까지 옛 위치에 남음. 옮긴 뒤 물리 변환 동기화를 한 번 부름.
- 에디터가 포커스를 잃으면 Play 중에도 프레임이 멈춤(백그라운드 실행 꺼짐). 키 입력 흉내로 Q/E 회전을 확인하려다 프레임이 안 넘어가서 못 함. 내부 뷰 네 방향 화면은 컨트롤러와 같은 카메라 계산(리그 높이, 내려다보는 각, 거리)으로 임시 카메라를 놓아 찍음. 1a에는 벽이 없어서 Q/E가 바꾸는 것은 카메라 방향뿐이라 결과 화면은 같음.

### 조절 가능한 것
- 구조 판 높이: 높을수록 통로가 기계 사이에 파인 길로 읽히지만 내부 뷰에서 뒤쪽 통로를 가림.
- 통로 바닥 색, 문 줄 색, 역할별 구조 판 색: 길, 방, 기계가 갈려 보이는 정도.
- 자리 바닥 색의 채도와 밝기: 낮을수록 탁해서 통로가 더 도드라짐.

## 5. 씬 구성

### 구현 방식
1. `ShipBlockout_Structure.unity`를 파일째 복사해 `ShipBlockout_Network.unity`를 만들고 복사본만 고침. 원본 씬은 열지도 않음.
2. 복사본에서 형식 1 생성기, 구조층 표현, 변 편집기를 뺌. 방 조명 그룹을 지움. 가구 그룹은 문 줄 그룹으로 이름을 바꿈.
3. 카메라 리그, 플레이어, 별빛, 외부 궤도 카메라, 컨트롤러는 그대로. 컨트롤러가 읽는 벽 그룹과 외피 그룹은 빈 채로 남김.
4. 씬 파일에는 빈 그룹과 미리보기 컴포넌트만 저장됨. 판은 Play 때마다 만듦.

### 여기서 터진 것
- 작업 시작 때 에디터는 다른 씬(`Prototype_SeedShip`)에서 Play 중이었음. 그 Play를 끄고 작업함. 그 직후 콘솔에 이전 세션의 임시 코드가 남긴 파괴된 캐릭터 컨트롤러 접근 예외가 반복해서 찍혀 있었고, 스크립트 다시 컴파일(도메인 리로드) 뒤 사라짐. 이 작업의 코드와는 무관함.
